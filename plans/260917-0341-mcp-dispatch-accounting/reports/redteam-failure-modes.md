## Finding 1: The aggregate is keyed on two frame fields that do not exist on any persisted frame

- **Severity:** Critical
- **Location:** Phase 3, sections "Architecture", "Implementation Steps" (step 1), "Function / Interface Checklist"; contradicting Phase 2, section "Parse contract for `InvocationRecord`"
- **Flaw:** Phase 3 freezes the consumed frame as `{ id, idempotencyKey, attachmentId, intent, state, startedAt, settledAt?, error?, result?, checksum }` and defines the row key as `frame.intent.name` and the latency pair as `settledAt − its own startedAt`. The persisted record has **no `intent` object** (`name` is a top-level string) and **no `startedAt`** (it is `createdAt`). Phase 2's parse contract correctly lists `name (:25)` and `createdAt (:42)` as top-level fields — so Phases 2 and 3 disagree about the same record, and Phase 3 is the one that is wrong. Phase 3's step 1 tells the implementer to derive the type from `invocation-ledger.ts:19-45`, but the type written into the phase is not what that range declares.
- **Failure scenario:** Phase 3 is implemented from its own text. `frame.intent.name` is `undefined` for every frame ⇒ `rows = []`, all 19,096 admitted frames land in `unattributed`; the Sub-tab renders zero rows (violating Success Criterion 1 and the plan's Goal 1). If the implementer instead falls back to `frame.intent?.name ?? 'unknown'`, every dispatch collapses into a single `unknown` row — silently collapsing 83 real tool names. Independently, `settledAt − startedAt` is `NaN` for every frame ⇒ `p50Ms`/`p95Ms` are `NaN`, `null`, or `0` depending on the nearest-rank guard — a measured-looking latency column with no measurement behind it. The plan forbids rendering unknown data as `0` (Goal 4) and this path produces exactly that.
- **Evidence:** `src/main/session/invocation-ledger.ts:19-45` (interface: `name: string;` at `:25`, `createdAt: number;` at `:42`, `settledAt?: number;` at `:43` — no `intent`, no `startedAt`); live-store probe: `framesWithIntentField=0`, `framesWithStartedAt=0` across all 19,096 admitted frames; sample persisted key set `["formatVersion","id","attachmentId","requestId","idempotencyKey","name","paramDigest","policyDigest","policyVersion","recordedVisibility","state","dispatchStage","authoritySnapshot","createdAt","result","settledAt","checksum"]`; writer side is `name: intent.name` at `src/main/session/invocation-ledger.ts:394` (a local parameter name, never a frame field); Phase 2 correctly says `name (:25)` at `phase-02-line-level-reader.md:80`.
- **Suggested fix:** Replace Phase 3's frozen type with the real one (`name`, `createdAt`), set `Row key = frame.name`, and set the latency pair to `settledAt - createdAt`. Add a compile-time guard that the aggregate module imports the `InvocationRecord` type rather than re-declaring it.

## Finding 2: The reconciliation invariant is specified so that it is FALSE on the live store, and the phase demands that it hold

- **Severity:** Critical
- **Location:** Phase 3, section "Requirements" (`reconcile()`), "Implementation Steps" step 3, "Test Scenario Matrix" U6/U7; plan.md "Success Criteria" line 130
- **Flaw:** `classified` is defined as "number of admitted frames attributed to a row" (i.e. a **frame** count) while `compositeKeys` is a **distinct-key** count, and `holds = classified + unattributed === compositeKeys`. Those are equal only when no composite key appears on more than one admitted frame — i.e. only when `superseded === 0`. The same phase requires `superseded` to be a normal, reported population (`calls` = distinct composites, `frames` = raw frames, `superseded = frames - calls`). So the invariant's truth condition is `superseded === 0`, and the plan asserts it "prints and holds". The fixture U6 (10 admitted / 10 keys) only passes because the fixture has no duplicates.
- **Failure scenario:** On the live store the Hub prints `classified 19096 + unattributed 0 == composite keys 18884` and marks it FAIL, permanently, on a healthy system. Phase 4's matrix R3 then asserts `holds === false` renders a `FAIL` token — so the FAIL chip becomes the steady state of the feature, and the one signal meant to make residue auditable becomes noise every operator learns to ignore. Worse: because the numbers are *close* (212 of 19,096), a real regression (say a whole partition of frames failing admission) hides inside an already-red invariant.
- **Evidence:** measured `admitted=19096`, `distinctComposites=18884`, `duplicateCompositeFrames=212` ⇒ `19096 + 0 ≠ 18884`; `phase-03-per-name-aggregate.md:22` (`classified`/`unattributed`/`holds`/`line`), `:62` (`frames - calls`), `:69` (`holds = classified + unattributed === compositeKeys`), `:93` (U1 expects `superseded === 1` alongside a passing reconciliation assumption); `plan.md:130`; `phase-04-delivery-surface.md:107` (R3 FAIL token).
- **Suggested fix:** Make the invariant population-consistent: `classifiedComposites + unattributedFrames === compositeKeys` where `classifiedComposites` counts distinct composites credited to a row, and report `supersededFrames` beside it as a separate disclosed population. Otherwise every "holds" assertion must be conditional on `superseded === 0`, which is never true in production.

## Finding 3: The Phase 6 emitter records every `core.*` outcome as success because `invokeCore` is async and the `finally` fires at promise-return time

- **Severity:** Critical
- **Location:** Phase 6, section "Implementation Steps" step 3
- **Flaw:** The prescribed wrapper is
  `try { return invokeCore(mappedEarly, params); } catch (err) { outcome = 'error'; …; throw err; } finally { emitCoreAttempt({ … outcome, errorCode, durationMs: Date.now() - t0 }); }`.
  `invokeCore` is declared `async`, so it returns a Promise that is **not awaited**; the `finally` block therefore runs synchronously the moment `invoke()` returns the pending promise — before `getCore()` has even opened SQLite, and before any store method has been called. `outcome` is always `'ok'`, `errorCode` is always `undefined`, and `durationMs` measures the synchronous prologue instead of the attempt. The plan's own requirement — "The emit runs in its own `try/catch` **after** the outcome is known" — is violated by the code the same section supplies.
- **Failure scenario:** A `core.*` call fails with `CORE_UNAVAILABLE` or `CAPABILITY_NOT_FOUND` (both thrown from inside the async body — `scripts/antifan-omp-mcp.cjs:530`, `:539`). The caller correctly sees the error, and the new store records `outcome: 'ok'`, `durationMs: 1`. The suite's only evidence of `core.*` reliability is therefore fabricated in the exact way the plan itself documents as the incident that motivated Phase 5's anti-fabrication copy. Because the record *is* written, every Phase 6 test in the matrix still passes: T6-2 asserts "exactly one bounded record per attempt containing method, requestedAs, outcome, durationMs" and one record does appear.
- **Evidence:** `scripts/antifan-omp-mcp.cjs:522` (`async function invokeCore(method, params)`); `:1535` (`return invokeCore(mappedEarly, params);` — the call site the plan wraps); `:530-540` (errors thrown from inside the async body); `phase-06-core-proxy-emitter.md:74-82` (the wrapper and the "after the outcome is known" requirement), `:92` (T6-2), `src/main/telemetry/fallback-recorder.ts:43-72` (the fabrication incident the plan cites).
- **Suggested fix:** Do not use `try/finally` around a returned promise. Capture and chain it: `const p = invokeCore(mappedEarly, params); p.then(() => emitCoreAttempt({outcome:'ok',…}), (e) => emitCoreAttempt({outcome:'error', errorCode: e?.code ?? 'ERROR', …})); return p;` — or `return invokeCore(...).finally(...)` on the *derived* promise. Add a negative test: force `invokeCore` to reject and assert the emitted record carries `outcome:'error'` and a non-zero `durationMs`.

## Finding 4: The reader blocks the Electron main process for 15-25 s per refresh, and the memo that is supposed to absorb it can never hit

- **Severity:** Critical
- **Location:** Phase 1, "Requirements" (Non-functional: "thin, synchronous, read-only function"); Phase 2, "Architecture"/"Cost sanity"; Phase 4, "Requirements" (memo key) and Risk Assessment; plan.md Design Decision 6
- **Flaw:** Two independent defects compound. (a) The whole pipeline is synchronous on the main process: `censusStore` is mandated "synchronous" and hashes **the content of every file** (`sha256(readFileSync(name))`), then the reader reads and parses every file again. My single read+parse+checksum+identity pass over the live store measured **11.4 s**; adding the census content-hash pass puts one `getState()` in the 15-25 s range. There is not a single yield point, whereas the ledger's own boot replay deliberately yields every 25 files. (b) The memo key is `sha256(sorted(name:size:mtimeMs)) + '|' + asOf`. `asOf` is the snapshot time the payload prints; it is not derivable from the file set the memo hashes, so any value the service can supply changes on every call (or is, circularly, an output of the work the memo exists to skip). And because the store is live and appended to by every dispatch, the size/mtime component is invalidated by any single MCP call. The memo is therefore structurally a no-op: every Hub tab click costs a full double pass.
- **Failure scenario:** An operator clicks the new Hub tab while an agent is mid-run. The main process event loop is blocked for ~20 s: `ipcMain` handlers for browser dispatch stop running, the terminal PTY pump stops, tab lifecycle and the `settleInFlightForShutdown` path cannot run, and any MCP dispatch routed through the desktop bridge times out against the caller's 240 s budget or is refused by the proxy's autoheal. The renderer (separate process) still repaints, so the UI looks alive; the control plane it is reporting on is frozen. Nothing in the plan detects or bounds this: the memo never helps, the CLI cannot share the memo, and `--no-memo` exists only in the CLI.
- **Evidence:** `phase-01-census-...md:57` ("Implement `censusStore` … as a thin, **synchronous**, read-only function"); `phase-02-line-level-reader.md:29` ("a full independent pass over the live store measures 7.9 s"; my independent measurement: 11,398 ms); `plan.md:57` and `phase-04-delivery-surface.md:25` (memo key includes `asOf`); `src/main/session/invocation-ledger.ts:131-135` (the writer *does* yield: `if (++fileIdx % 25 === 0) { setImmediate(resolve); await promise; }`); `src/main/session/invocation-ledger.ts:176` (whole-file `readFileSync`); largest partition 143,203,927 B (1,140 lines ⇒ ~125 KB average line, so a bounded per-line read is also the only way to stay under frame limits).
- **Suggested fix:** Move the scan off the main thread (worker thread or a `child_process` running the same electron-free reader, which the CLI already proves works), stream per line instead of whole-file `split`, and either drop `asOf` from the memo key or define `asOf` as a pure function of the hashed file set. Add a hard budget test: `getState()` must return within N ms or yield `UNMEASURED` with a named reason rather than block.

## Finding 5: `CENSUS_DRIFT` is unreachable, and the census-vs-read torn snapshot it was invented for is undetectable

- **Severity:** Critical
- **Location:** Phase 3, "Implementation Steps" step 5 and Success Criterion "`CENSUS_DRIFT` returns `UNMEASURED`"; Phase 1, Risk Assessment ("Same-size in-place rewrite (compaction) mixes snapshots"); plan.md Design Decision 6
- **Flaw:** The guard is specified as "if the census hash of a **re-read** file differs while its size/mtime are unchanged". No phase defines the re-read, when it happens, or what it is compared against. On a memo hit the census is skipped entirely (that is the point of the memo), so no comparison is possible; on a memo miss there is no previous census to compare to. There is no persisted prior snapshot. The guard as written can only ever fire in the hand-built U9 fixture. Meanwhile the real hazard is unguarded: `censusStore` hashes content at time T, the reader later reads exactly `size` bytes at time T+n, and between them the ledger may have replaced the file — its compaction path writes a temp file and renames over the partition. The reader then aggregates content that does not match the census it reports, and nothing detects it.
- **Failure scenario:** The app restarts. `initialize()` replays every partition and, for any partition containing a `claiming`/`in_progress` frame, compacts it (`writeFile(temp)` → `rename(temp, filePath)`), rewriting a large partition as a small coalesced one. The Hub is opened while boot replay is still compacting (or `claimOwner` triggers compaction at 200 uncompacted frames during a busy agent run). `censusStore` records the pre-compaction size and content hash; the bounded read opens the file after the rename and reads the compacted content. It ends with `\n` (compaction always appends a trailing newline), so the tail is not torn; every remaining frame's checksum is valid, so nothing is `CHECKSUM_MISMATCH`; no bytes are past the bound, so nothing is `POST_CENSUS_APPEND`. The payload reports `status: MEASURED`, `asOf`, and a `censusHash` that describes bytes it never read, with `superseded` silently collapsed toward 0. This is exactly the "mixes snapshots" failure the plan's own risk row claims to answer with `CENSUS_DRIFT`.
- **Evidence:** `phase-03-per-name-aggregate.md:72` ("the census hash of a re-read file"), `:101` (U9 is a synthetic fixture only); `plan.md:57` and `:169`; `phase-04-delivery-surface.md:25` (memo key on size/mtime, so a memo hit never re-runs the census); `src/main/session/invocation-ledger.ts:843-844` (`await fs.promises.writeFile(tempFile, content, 'utf8'); await fs.promises.rename(tempFile, filePath);`), `:841` (trailing newline written), `:212`+`:255-257` (boot replay compacts whenever a `claiming`/`in_progress` frame is seen), `:478-480` (`currentFrames >= maxHotRecords` ⇒ compaction on the hot path); 222 `in_progress` frames present in the live store at review time.
- **Suggested fix:** Make the drift check executable: after the bounded read, re-`stat` each file and re-hash anything whose `mtimeMs` changed, or (cheap) read via an fd opened once and verify `fstat.size` and a re-read of the last N bytes before/after; on mismatch emit `CENSUS_DRIFT` and refuse a stable total. Add a test that compacts a fixture file between the census and the read and asserts `UNMEASURED/CENSUS_DRIFT` rather than a stable total.

## Finding 6: The `POST_CENSUS_APPEND` boundary is classified last, is unobservable from a bounded read, and has no test

- **Severity:** High
- **Location:** Phase 2, section "Classification order (per line)", step 2, and "Success Criteria" ("a synthesized append during the read appears as `POST_CENSUS_APPEND`, not in the admitted set")
- **Flaw:** Three separate holes in one rule. (a) The fixed order puts `POST_CENSUS_APPEND` at **step 4**, *after* step 3 has already returned `ADMITTED` — a line can satisfy both, and the spec does not say which wins; the Success Criterion says the append must not be in the admitted set, i.e. the boundary check must come first. (b) If the reader reads exactly the censused `size` bytes, the bytes past the bound are never observed — reporting "bytes beyond that bound are counted as `POST_CENSUS_APPEND`" requires a second `stat` that the plan never mentions, so as specified the class is unreachable except by accident. (c) There is no row for it in the Phase 2 test matrix (T1-T8, N1, N2, Q1, Q2, I1, I2, C3, C4, E4), so the only place the claimed behaviour appears is prose in the Success Criteria.
- **Failure scenario:** The implementer follows step 2's bounded read and step 4's ordering; the guard becomes dead code. A partition that grows by one full frame during a 240 MB read yields an aggregate that includes the new frame while its `asOf` and census claim it did not — the run is not reproducible (Success Criterion "Two runs on one frozen snapshot copy are byte-identical modulo `asOf`" is tested only on a frozen copy, so this never surfaces in acceptance; see Finding 10). Alternatively, if the implementer moves the boundary check first and reads `size+1` bytes to detect the overflow, the "+1" byte is a partial UTF-8 sequence that must be handled deliberately or it becomes a spurious `TORN_TAIL`. The plan resolves neither ordering.
- **Evidence:** `phase-02-line-level-reader.md:59-69` (classification order, `POST_CENSUS_APPEND` last), `:94` (bounded read), `:110` (Success Criterion), `:114-134` (matrix with no `POST_CENSUS_APPEND` row); `plan.md:57` ("bound every file at the byte length recorded in its census entry"); `src/main/session/invocation-ledger.ts:802` (`JSON.stringify(frameWithChecksum) + '\n'` appended by `fs.promises.appendFile` at `:806`).
- **Suggested fix:** Move the byte-boundary test to step 1, define the class as "the line whose start offset is `>= censusedLength`", implement it by comparing the running byte offset during the read, and add explicit matrix rows for (i) a frame appended during the read and (ii) a truncated multi-byte tail.

## Finding 7: Panel B's two core requirements are mutually exclusive, and nothing owns root enumeration

- **Severity:** High
- **Location:** Phase 5, "Requirements" (Functional and Non-functional), "Function / Interface Checklist"; plan.md Design Decision D
- **Flaw:** The phase requires the reader to "mirror the **writer's** root resolution, not an idealized one", and simultaneously forbids a `process.cwd()` fallback ("never a silent `process.cwd()` fallback, never `0`"). But the writer's effective resolution *is* `process.cwd()` on exactly the configuration that produced the second live store: the only production call site passes the resolver's result straight through, and when the resolver yields `''` the default parameter does not fire, so `path.join('', '.antifan', 'telemetry', 'gaps.jsonl')` is appended relative to the process CWD; when the resolver is absent the argument is `undefined` and the default `process.cwd()` fires. `''` and "absent" therefore converge on the same CWD-relative path. "Mirror the writer" and "never use CWD" cannot both hold. Separately, `readSelfReport(root: string)` takes **one** root, and the requirement to produce per-root rows never says who enumerates the roots — the only module that owns the registry-based resolution is on Phase 2's forbidden-import list for the reader module.
- **Failure scenario:** On a session where the registry root is unbound and no `THEME_WORKSPACE_ROOT`/`ANTIFAN_WORKSPACE_ROOT`/`WORKSPACE_ROOT` is set, the writer appends to `<cwd>/.antifan/telemetry/gaps.jsonl` while the reader, honouring the no-CWD rule, reports `NO_DATA` with the env-derived path. Panel B shows a hole for the file that is actively being written — the "absence is never rendered as a measured zero" property is preserved, but the panel's whole purpose (making divergence visible) fails, and the plan's Success Criterion "the 4 pre-fix fabricated records are displayed" fails with it. If the implementer instead resolves the roots inside the service, that service now imports the runtime the Phase 2 "Must not import" list forbids, and the electron-free guarantee that Phase 4's CLI depends on is lost.
- **Evidence:** `src/main/tools/browser-capabilities.ts:968` (`recordFallbackTelemetry(params, getWorkspaceRoot ? getWorkspaceRoot() : undefined)`); `src/main/telemetry/fallback-recorder.ts:122` and `:128` (`baseDir = process.cwd()`), `:134`, `:153` (`fs.appendFileSync(logPath, …)` resolves relative to CWD; `logDir` at `:135` is `path.dirname(logPath)` = `.antifan/telemetry`); `src/main/control-plane/control-plane-runtime.ts:248-291` (`getWorkspaceRoot()`, registry check at `:266`, env chain at `:276`, `resolved = ''` at `:282`/`:285`); `phase-05-self-report-panel.md:26`, `:74`, `:97`, `:116`; `phase-02-line-level-reader.md:145` ("Must not import: `control-plane-runtime.ts`"); live roots confirmed by directory listing: `E:\Work\apps\AntiFan\.antifan\telemetry\gaps.jsonl` (89,379 B) and `E:\Work\.antifan-data\.antifan\telemetry\gaps.jsonl` (1,107 B).
- **Suggested fix:** State the writer's resolution as a closed contract including the CWD-relative terminal case, have the reader accept an explicit `roots: string[]` from a caller that is allowed to import the runtime (the service), and add a decision rule for the CWD case — either disclose the CWD-relative path as one of the roots with its provenance, or prove by measurement that the writer can no longer reach that branch.

## Finding 8: The new compile gate has no defined behaviour for `UNMEASURED`, and its "equal totals" rule fires on absent totals

- **Severity:** High
- **Location:** Phase 7, "Requirements" (functional, gate rules 1-4), "Implementation Steps" steps 1-4, "Risk Assessment" row 1
- **Flaw:** The gate's rule 4 is "any total in one payload equal to a total in the other". On any machine with no data root (fresh clone, CI-less peer machine, a data root that is missing or unreadable) both payloads are `UNMEASURED` with `totals: null` — and `null === null` is true, so the gate fails the build on pre-existing state. The plan's risk row answers this with "derive every threshold and count at run time", which does not address a *comparison between two absent values*; and the gate is specified to "build both payloads … against a fixture directory" while T7-2 requires it green "against the real tree", so it is unclear whether the compile-time invocation reads the fixture or the live 240 MB store. Rule 2 ("any key matching a ratio-like pattern") is applied to keys, and `rows[*].errors` is a histogram whose keys are **dynamic error codes** produced by the writer, so a future code containing e.g. `RATE` would fail the build from data rather than from a design change. Rule 3 ("any Panel A field reachable from Panel B rows") states no reachability mechanism. There is also an ordering hazard the plan explicitly reasons about but gets wrong: wiring the gate at `package.json:24` **before** `prune-orphan-emit` and `copy-static` means a red gate skips static asset copying after `tsc` has already emitted fresh JS.
- **Failure scenario:** A developer pulls the branch on a machine without `E:\Work\.antifan-data` and runs `npm run compile`. `tsc` emits fresh `.compiled/src/renderer/toolbar.js` containing the 8th tab; the gate fails on `null === null`; `copy-static` never runs, so `.compiled/src/renderer/toolbar.html` (copied at `copy-static.mjs:36-49`) is the pre-change file with only seven nav buttons. `scripts/run-electron.cjs` only compiles when the bundle is missing, so the app now launches with a new `toolbar.js` and an old `toolbar.html`: `document.getElementById('tabNavMcpDispatch')` is `null`, `HUB_NAV_BUTTONS['mcp-dispatch']` is `null`, the click listener is skipped by the optional chain, and the tab silently never appears — with no compile error to explain why. The same mismatched-artifact state is the failure mode of any gate failure mid-chain, and it is the state the repo is left in.
- **Evidence:** `phase-07-gates-docs-and-followup.md:19` (rule 4), `:20` (`package.json:24` insertion point), `:58` (fixture-built payloads), `:85` (T7-2 "against the live service payloads"), `:114` (risk row answering with run-time derivation); `package.json:24` (`tsc -p ./ && node scripts/check-mcp-budget-dominance.mjs && node scripts/prune-orphan-emit.mjs && node scripts/copy-static.mjs && npm run build:extension`); `scripts/copy-static.mjs:36-49` (renderer asset copy) and `:106`; `scripts/check-emit-integrity.mjs:11-13` (documenting that `scripts/run-electron.cjs` only compiles when the bundle is missing); `phase-03-per-name-aggregate.md:24` (empty/unreadable ⇒ `UNMEASURED`).
- **Suggested fix:** Define explicit gate semantics per `status`: skip comparison rules when either payload is `UNMEASURED`, and require equal totals only when both totals are non-null and at least one is non-zero. Pin the gate to a committed fixture for compile-time use and run the live-payload check only in the acceptance lane. Move the gate to the end of the chain (after `copy-static`) so a red gate cannot leave a half-updated `.compiled`.

## Finding 9: Phase 6 writes to a store that no phase reads, its appends can be lost or interleaved, and the stated hole is narrower than reality

- **Severity:** High
- **Location:** Phase 6, "Requirements" (Functional, Non-functional), "Implementation Steps", "Success Criteria"; Phase 7, docs step 6; plan.md Success Criteria line 136
- **Flaw:** Phase 6 defines an emitter and a rotation discipline, but **no phase defines a reader, a panel, a row set, or an IPC path for `core-attempts-*.jsonl`**. Phase 5 is Panel B (self-report) only; Phases 1-4 are the ledger only. The plan nonetheless grades `core.*` as satisfied "either as measured proxy attempts (Phase 6 landed, `omp-proxy` provenance, `proxy-attempt` unit) or as an explicit labelled hole" — landing the emitter satisfies the letter of the criterion while nothing in the Hub shows a single `core.*` row. Three further gaps: the requirement "append asynchronously and never await it before returning the caller's result" means records are lost whenever the proxy exits soon after the last call, which is the normal lifetime of a stdio MCP server; concurrent unawaited `appendFile` calls on one path mean N open/append/close sequences with no ordering guarantee (on Windows this can interleave and produce the torn lines the plan's own Panel-A reader would classify as residue); and the "Codex is the only hole" claim is incomplete because the proxy is also launchable without `antifan-agent.cjs` at all.
- **Failure scenario:** Phase 6 lands and Phase 7 documents `core.*` provenance in `docs/operations.md`. An operator asks "which `core.*` tools are actually used?" and finds no surface: the emitter's records sit in an unread directory, and the Hub's coverage table still shows `core.*` as a labelled hole. Any records that were written are unattributable to a rotator failure or to the "too few records, process exited first" race, and because the write is unawaited the plan's own T6-2 ("exactly one bounded record per attempt") is inherently flaky under a spawned-child test.
