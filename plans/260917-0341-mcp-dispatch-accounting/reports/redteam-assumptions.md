## Finding 2: The Phase 6 emitter is structurally blind to every `core.*` failure and every duration, because `invokeCore` is async and the plan wraps it without awaiting

- **Severity:** Critical
- **Location:** Phase 6, section "Implementation Steps" step 3 (the wrap snippet) and Success Criteria bullet 2
- **Assumption:** `try { return invokeCore(...) } catch { outcome='error' } finally { emit(...) }` observes the call's outcome and its duration.
- **Condition that breaks it:** `invokeCore` is `async function invokeCore(method, params)` (`scripts/antifan-omp-mcp.cjs:522`), so it **always** returns a promise. In `async function invoke`, `return invokeCore(...)` inside `try` does not await: the `finally` block runs on the same synchronous turn, i.e. **before** the promise settles. Therefore `outcome` is always `'ok'`, `errorCode` is always `undefined`, and `durationMs = Date.now() - t0 ≈ 0`. The `catch` branch is dead code for every real error path (`CORE_UNAVAILABLE` `:531-533`, `CAPABILITY_NOT_FOUND` `:539`, any store throw) because those arrive as rejections. Phase 6's success criterion "exactly one bounded record per attempt containing `method`, `requestedAs`, `outcome`, `durationMs`" is met in form and false in content: the panel's `core.*` outcome mix reads 100 % `ok` with ~0 ms latency, i.e. it claims the exact opposite of the truth exactly when `core.*` is failing. The plan's own escape ("`emitCoreAttempt` never awaits in the caller's path", phase-06:27/`:82`) is what makes it unfixable by adding `await` inside `finally` without changing the reported semantics.
- **Evidence:** `phase-06-core-proxy-emitter.md:74-82`; `scripts/antifan-omp-mcp.cjs:522-542` (`async function invokeCore`, store calls at `:541`), `:1533-1536` (`return invokeCore(mappedEarly, params)` inside `async function invoke` `:1505`), `:1928-1930` (rejections become `{isError:true}` at the handler); `phase-06:92` (the success criterion).
- **Suggested fix:** either (a) `const result = await invokeCore(...)` inside the `try` and emit *after* the value is known but *without* awaiting the write (`.then`/detached append) — the hot path still never awaits I/O; or (b) if the early `return` shape must be byte-preserved, emit from a `.then/.catch/.finally` attached to the promise (`return p.then(r => {emit('ok'); return r;}, e => {emit('error'); throw e;})`). Add a Phase 6 matrix row that forces a store failure (e.g. `SUPER_CORE_DB` pointed at a directory) and asserts the record's `outcome==='error'` and `durationMs > 0`.

## Finding 5: The memo key contains `asOf`, so the memo cannot hit for the service; and the pass it fails to absorb hashes ~230 MiB of file content synchronously on the Electron main thread

- **Severity:** High
- **Location:** Phase 4, Requirements (memo key) and step 1; Phase 3 step 4; Phase 1 steps 2-3
- **Assumption:** "warm path is a memo, not a store" — a repeat call is cheap because the memo is keyed on the file set's `size:mtimeMs`.
- **Condition that breaks it:** the key is `sha256(sorted(name:size:mtimeMs)) + '|' + asOf` (`plan.md:57`, `phase-04:25`, "no TTL; one entry, evicted on key change"). `asOf` is *injected*, not derived (`phase-01:57`: "`asOf` is **injected**, never read from the clock inside the function"), and the service has no other source for it than the wall clock at call time. With a fresh `asOf` per call the key never matches the previous entry ⇒ every Hub open re-runs the whole pipeline. The pipeline itself cannot be made cheap by a stat-only key, because `censusHash` is defined over **file contents** (`sha256(file)` inside the name/size/hash recipe, `phase-01:20`, `:38`, `:58`) and Phase 3's `CENSUS_DRIFT` guard compares content hashes (`phase-03:72`). So the unavoidable per-call cost is: read + sha256 every byte of a 240.9 MB / 19,215-frame store, then `JSON.parse` each line and sha256 the canonical form of each frame — the plan's own basis is 4.7 s for the raw byte-read+split alone (scout-delivery-surface §0) and 2.9-13.7 s end-to-end (`plan.md:57`). Worse, `censusStore` is specified **synchronous** (`phase-01:57`, "thin, synchronous, read-only function") and `readAdmittedFrames` returns a plain object (`phase-02:19`), so that multi-second work executes inside an `async` IPC handler on the Electron **main** thread: every other IPC call, window event and the ledger's own append path queue behind it. If instead the service re-uses the cached `asOf` to make the key stable, the payload's `asOf` no longer describes when the data was read — the plan never specifies which of the two it means. Either way one of {memo hits, honest `asOf`} is false, and Success Criterion "Two runs on one frozen snapshot copy are byte-identical modulo `asOf`" (`plan.md:137`) is only satisfiable in the CLI, where memo is off by default (`phase-04:22`).
- **Evidence:** `plan.md:57`, `phase-01-census-and-contract-freeze.md:20`, `:38`, `:57-58`, `phase-03:71-72`, `phase-04-delivery-surface.md:25`, `:43`; measured 1,041 files / 229.7 MiB / 19,215 frames (this review).
- **Suggested fix:** make the snapshot identity self-consistent: derive `asOf` from the census (e.g. the newest `mtimeMs` in the file set, or the frozen-copy marker) so an unchanged file set yields an unchanged key *and* an honest timestamp; state explicitly that the reader runs off-thread (`utilityProcess`/worker) or asynchronously with a bounded chunked read, and add a service-level memo-hit assertion to the matrix (two `getState()` calls with no store change ⇒ one census pass, proven by an instrumented counter).

- **Severity:** High
- **Location:** Phase 4, Implementation Step 5 vs Phase 1 Requirement "Non-functional" and Phase 4 matrix C3

That precedent is a *guessing* ladder: it pushes `<REPO_ROOT>/.antifan-data/control-plane-v2/artifacts`, `<REPO_ROOT>/../.antifan-data/...`, `<REPO_ROOT>/../.antifan-canary/...` unconditionally (`build-report.mjs:792-796`). The acceptance evidence (`--store "<tmp freeze>"`) would not catch it because it always passes `--store`.
- **Evidence:** `phase-04-delivery-surface.md:80`, `:114`; `phase-01-census-and-contract-freeze.md:26`; `plan.md:65`; `scripts/lib/build-report.mjs:792-796`.

Add a matrix row that runs the CLI with `cwd` set to the repo root, no `--store`, no `ANTIFAN_DATA_ROOT`, and a real store present one directory up, and asserts `UNMEASURED` (not a silently measured real store).

## Finding 7: Panel B's "rotation-aware" contract double-counts records when rotation lands mid-read, and inherits an item the scouts explicitly labelled ASSUMED

- **Severity:** High
- **Location:** Phase 5, Requirements ("Rotation-aware and race-tolerant") and matrix T5-7
- **Assumption:** "re-glob after reading and report the file set with `asOf`" makes a mid-read rotation safe, because the file set is disclosed.
- **Condition that breaks it:** the writer rotates by `fs.renameSync(logPath, path.join(logDir, 'gaps-<Date.now()>.jsonl'))` when the live file is at the 10 MB cap (`fallback-recorder.ts:22`, `:143-149`). If rotation happens between the reader's glob and its read of `gaps.jsonl`, the reader either reads the renamed `gaps-<ts>.jsonl` (missing records) or, on a re-glob, reads the **same records a second time** under the rotated name — the plan says to re-glob and report the file set, and specifies no record-level dedupe or ordering key, so panel counts can exceed the number of events that ever occurred inside the panel whose entire purpose is honesty, and no gate covers it (Phase 7's gate only forbids **cross-panel** totals, `phase-07:19`). The scouts supplied the missing mechanism but flagged it **ASSUMED**: "Ordering: with no rotated file on disk to observe, ordering must key on mtime or the record's `timestamp`, not on filename (`.` sorts before `-`, and `Date.now()` suffixes only sort lexicographically while the digit count is stable) — **ASSUMED**" (scout-panels-gates §2). The plan promotes the glob but never names an ordering or dedupe contract, so the ASSUMED item is inherited silently.
- **Evidence:** `phase-05-self-report-panel.md:19`, `:28`, `:91` (T5-7 expects only "re-glob; the file set and `asOf` in the payload explain the difference"), `:118`; `src/main/telemetry/fallback-recorder.ts:22`, `:143-149`; `plans/260917-0341-mcp-dispatch-accounting/reports/scout-panels-gates.md:75`.
- **Suggested fix:** state the record ordering key explicitly (record `timestamp`, then file mtime, then a synthetic index) and make T5-7 assert **no double count**: rotate between glob and read, then assert `records.length` equals the number of distinct `(timestamp, primaryTool, fallbackTool, sessionId, notes)` tuples, with the surplus reported as a named `DUPLICATE_AFTER_ROTATION` class rather than folded into a count.

## Finding 8: The composite identity is built by string concatenation with no absence guard, so Phase 3's `unattributed` detector can never fire and identity-less frames silently collapse into one call

- **Severity:** High
- **Location:** Phase 2 Requirements (identity) + Phase 3 `reconcile()` definition and matrix U7
- **Assumption:** "a frame whose composite is absent is counted in `unattributed`" (phase-03:20), detected as "missing/blank `intent.name` or missing composite key" (phase-03:67).
- **Condition that breaks it:** the identity is constructed as `frame.attachmentId + '\u0000' + frame.idempotencyKey` (`phase-02:23`). When either field is absent, JS yields the **non-empty, truthy** string `"undefined\u0000undefined"`; a "missing composite key" check therefore never fires, and *every* identity-less admitted frame shares one composite. Since the reader admits on checksum alone and deliberately does **not** apply the ledger's structural rule (`invocation-ledger.ts:188`; Finding 3), nothing else rejects such a frame. Effect on the payload: `calls` for that group is deflated by (n−1), `superseded` inflated by the same amount, and `reconcile()` reports `unattributed: 0` with `holds: true` — the invariant that the plan calls its auditable honesty line reports success on exactly the input it was built to catch. Measured today the input is absent (0 frames missing `attachmentId`/`idempotencyKey`/`name`), which is what makes this a *plan* defect rather than a data defect: the guard's purpose is future/foreign input, and matrix row U7 can only pass because its fixture supplies a hand-built "missing" value that the production construction path cannot produce.
- **Evidence:** `phase-02-line-level-reader.md:23`; `phase-03-per-name-aggregate.md:20`, `:67-69`, `:99` (U7); `src/main/session/invocation-ledger.ts:188`; measured: 0 frames missing `attachmentId`/`idempotencyKey`, so U7 cannot be reached from real data.
- **Suggested fix:** build the composite from validated non-empty strings and return a discriminated result — `{ ok: false, reason: 'MISSING_IDENTITY_FIELD', field }` — counted in `unattributed` and in a new residue class; add a matrix row that runs the *real* pipeline (`readAdmittedFrames` → `aggregateByName` → `reconcile`) over a fixture line that is checksum-valid but lacks `attachmentId`, and asserts `unattributed === 1` and `holds === true` against the recomputed numbers (not against a constant).

## Finding 9: The proxy store's rotation bounds bytes but not file count, so Phase 6's own "bounded file count and size" criterion cannot hold, and its cap check sits synchronously on the hot path

- **Severity:** High
- **Location:** Phase 6, Requirements (rotation/cap) and Success Criteria bullet 4 / matrix T6-4
- **Assumption:** "rotate at a byte cap to `core-attempts-<ts>.jsonl`; refuse writes past the cap rather than growing without bound" keeps the store bounded.
- **Condition that breaks it:** rotation moves the growth from one file to *N* files and never deletes any: each rotation mints a new `core-attempts-<Date.now()>.jsonl`, and nothing caps the rotated count or prunes old ones. That is verbatim the discipline the plan documents as unbounded for the sibling store — "rotation happens at a 10 MB cap by renaming to `gaps-<Date.now()>.jsonl` … **with no cap on the rotated count and no pruning**" (`plan.md:146`) — and the new store has neither a reader nor a retention owner in this plan (Non-Goals: "Retention changes: the plan reports the retention caveat, it does not extend it", plan.md:41). So `phase-06:94` ("the store's file count and size stay bounded") and T6-4 ("bounded file count/size") are unachievable as designed. Two further consequences: (a) rotation is decided by a **synchronous `statSync` before appending** (`phase-06:83`) — a blocking syscall on the hot path of every `core.*` call, contradicting `phase-06:27` ("Never block… Append asynchronously"); and (b) the rotation is a read-modify-write on a directory shared by every proxy process that inherited the variable (one per MCP client session), so two processes rotating concurrently race — the plan's answer, "if rotation fails, refuse the write" (`:83`), converts the race into silently lost records with only a once-per-process stderr note ("report it once", `:83`).
- **Evidence:** `phase-06-core-proxy-emitter.md:24`, `:27`, `:73`, `:83`, `:94`, `:107`, `:118`; `plan.md:41`, `plan.md:146`; `src/main/telemetry/fallback-recorder.ts:22`, `:143-149`.
- **Suggested fix:** specify a bounded retention policy in the same phase (max rotated files, delete oldest, or a single fixed-size ring file), do the size check inside the async emit path (or key it on an in-memory counter initialised once at startup), and name the multi-writer case explicitly: one file per proxy pid (`core-attempts-<pid>-<ts>.jsonl`) with a cap, or a documented `proxyTelemetryBusy` refusal counted in the payload.

## Finding 10: The cost model is calibrated on one unpruned dev store, and the plan refuses the retention change that would make the calibration hold

- **Severity:** Medium
- **Location:** plan.md Design Decision 6 / Non-Goals; Phase 1 "Measured scale"; Phase 2 risk row
- **Assumption:** "the reader walks ~240 MB", "a full pass measures 4.7 s of raw byte-read+split on this host (2.9-13.7 s end-to-end)" and the memo makes repeats cheap — i.e. the store's size and growth rate are representative of where the feature runs.
- **Condition that breaks it:** the population is **append-only with no pruning for the files the reader adds**: `initialize()` and `pruneDeadPartitions()` both filter `endsWith('.jsonl')`, so `*.jsonl.quarantine-<ts>` and `*.jsonl.tmp-*` are never replayed and never unlinked (`invocation-ledger.ts:126`, `:142`, `:260-271`) — the plan itself states quarantine files are "retained indefinitely" (plan.md:47) — while live partitions grow per dispatch and are only coalesced per `idempotencyKey` at compaction. My measurement shows the store at 1,041 files / 229.7 MiB / 19,215 frames versus the plan's frozen 1,040 / 239 MB / ~19,077-19,119 lines within hours, and the largest single partition at 136.6 MiB with 50 lines > 1 MB and a 3.8 MB maximum line (scout-delivery §0, phase-01:46). The reader materialises the whole admitted set (`readAdmittedFrames` returns `{ admitted, … }`, phase-02:19) including `result` payloads of that size, in the Electron main process, and the memo has no declared size bound. With retention explicitly out of scope, the "warm path" degrades monotonically with normal product use: the tab's cost is a function of lifetime, not of the current snapshot, and Failure mode is a main-process stall whose length the plan can only bound by an assertion made on one developer machine. The plan's risk table covers "store grows during a read" (drift) but has no row for "store grows across releases".
- **Evidence:** `plan.md:41`, `:47`, `:57`; `phase-01-census-and-contract-freeze.md:46`; `phase-02-line-level-reader.md:19`, `:168`; `src/main/session/invocation-ledger.ts:126`, `:142`, `:260-271`; measured 1,041 files / 229.7 MiB / 19,215 frames / largest partition 136.6 MiB (this review).
- **Suggested fix:** add a hard input bound to the reader (max files, max bytes, max frames) with a named `POPULATION_TRUNCATED` outcome instead of an unbounded pass; state the retention dependency as an explicit blocking precondition on the Phase 5/`260901-1736` owner (the plan already does this for `gaps.jsonl` only); and put the latency budget for the Hub call in the acceptance criteria (e.g. "tab open ≤ X ms on the frozen snapshot, measured, with the census cost reported separately") so the 240 MB figure becomes a bound the implementation must meet rather than a measurement it inherits.
