# Phase 4: Delivery Surface (Service, IPC, Hub Tab, CLI)

## Overview

Expose the Phase 3 envelope through four surfaces that share **one** reader: a worker-backed, memoized main-process service; one read-only, **sender-gated** IPC handler; one new tab in the existing Workflow & MCP Hub; and a deterministic CLI harness that proves the same reader runs outside Electron. No advertised MCP tool is added, no raw frame crosses IPC, and no second display panel exists — the self-report panel is **deferred** to its own follow-up plan (`plan.md` Non-Goals), so this phase builds no second panel, no second IPC channel, no second preload method and no Panel A/B toggle. The Hub renders **one** panel over the ledger population plus an explicitly labelled `core.*` hole that Phase 5 either fills or leaves named.

## Requirements

- **Functional:**
  - `McpDispatchService.getState()` returns the envelope; `clearCache()` forces a re-read; `getMcpDispatchService()` is a module singleton mirroring `getCoreHealthService()` (`src/main/diagnostics/core-health.ts:791-795`), with memo fields mirroring `cliCache`/`cliInFlight` (`:273-274`) and `clearCache()` mirroring `:370-372`.
  - **The pass and the aggregation run in a `node:worker_threads` worker, never on the Electron main thread (plan.md constraint G).** The service is the **only main-process caller**. It spawns a worker over the compiled, electron-free module (`src/main/diagnostics/mcp-dispatch-accounting.ts` → `path.join(__dirname, 'mcp-dispatch-accounting.js')`), and that worker runs Phase 3's `accountStore({ storeDir, asOf, memo: false })`, which wraps Phase 1's `runCensusPass` — so aggregation and the pass share one thread, as `phase-01`'s same-thread rule requires, and this phase adds no reader step of its own (`phase-01:256`, `phase-03:129`, `phase-03:184`). The worker protocol, the `PASS_BUDGET_MS` check between files, the `terminate()`-on-expiry and the caller-side bounded await are **frozen in Phase 1** (`phase-01:89`, step 5, `:197-198`); this phase consumes that contract and must not fork it — Phase 1's "main-thread API" **is** this service's `getState()`, which `phase-01:89` names explicitly, so there is exactly one spawn path in the codebase. The contract in one place:
    - worker → main, exactly one message, then exit: the **projected `McpDispatchAccount`** — a complete envelope, `MEASURED` or `UNMEASURED`, never a fault object and never a raw frame set.
    - main → worker: `workerData` only (`{ storeDir, asOf, mode }`); no `postMessage` in the other direction, no shared state.
    - `getState()` returns within `PASS_BUDGET_MS + worker start + one file read` even if the worker hangs (a hung worker is the case Phase 1's caller-side await exists for), and in that case returns `status: 'UNMEASURED'`, `reasonCode: 'READ_BUDGET_EXCEEDED'`. A worker that dies (`'error'`, or `'exit'` with no message) yields `'SERVICE_FAILED'` through this phase's `unmeasuredEnvelope`. **The main process never holds the admitted frame set and never calls `readAdmittedFrames`/`accountStore`/`runCensusPass` outside the worker** — Phase 1 asserts the single call site (`phase-01:207`, `:217`). **`runPopulationSweep` is the one deliberate exception**, and it is allowed *because* of the rule it looks like it breaks: the module's `computePopulationMemoKey` requires a `bucket: CensusBucket` per entry, so computing the memo key locally would mean re-deriving the module's bucket classifier on the main thread — a second source of truth for a rule the module already owns. Stage A is metadata-only (`readdirSync` + one `statSync` per file, **no byte read, no frame, no fold**), the module itself documents the delivery surface as its main-thread caller (`:703-705`), and a disagreement between the two key computations costs a memo miss, never a wrong answer. The honest cost is a **second metadata sweep** when the worker runs (once for the key, once inside the pass); it is bounded to directory entries and stats, and the 11.8 s live pass is dominated by the byte read, so the duplication must stay visible in the risk table rather than be rediscovered as a mystery cost.
    - `PASS_BUDGET_MS`, `MAX_CENSUS_BYTES`, `MAX_CENSUS_FILES` and `IN_PROCESS_YIELD_INTERVAL_FILES` are Phase 1's exported constants (`phase-01:195`); this phase inlines **no** literal and declares no second budget option.
  - **The two bounded outcomes are rendered differently, on purpose (`plan.md` constraint G).**
    - *Time* budget expiry ⇒ `status: 'UNMEASURED'`, `reasonCode: 'READ_BUDGET_EXCEEDED'`, `census: null`, `rows: []`: a partial in-memory fold cannot be trusted, so it is discarded and there are no rows at all.
    - *Input* ceiling (`MAX_CENSUS_BYTES`/`MAX_CENSUS_FILES`) ⇒ rows **are** rendered, every row marked `lowerBound: true`, with `totals.truncation = { ceiling, filesRead, filesSkipped, order }` and a label reading `partial: N of M files`. `order` is `'mtimeMs-desc,name-asc'` — the selection order is part of the disclosure, because a name-sorted prefix would render every late-sorting tool as "never called"; the payload also carries the covered window (oldest and newest `mtimeMs` among the files actually read) so a partial answer reads as "recent activity, not all history". Truncation is the same class of incompleteness as a short read and is disclosed the same way; silently reading part of the store and blanking the feature are both failures.
    - **Cross-phase fork: RESOLVED (2026-09-17) — this bullet records the outcome, not an open question.** The fork was real and is now closed in `plan.md` constraint G: an *input* ceiling renders rows over the read prefix (all `lowerBound: true`, `totals.truncation = { ceiling, filesRead, filesSkipped, order }`, covered window disclosed), a *time* budget expiry stays fail-closed `UNMEASURED`/`READ_BUDGET_EXCEEDED` with no rows, and only the degenerate `filesRead === 0` case is `UNMEASURED`/`POPULATION_TRUNCATED`. Phase 1 and Phase 3 have both been revised to these semantics; the reasoning is that a partial *fold* is untrustworthy while a partial *file set* is merely incomplete and countable, so blanking the feature whenever the store is large would fail exactly when the data matters most.
  - **Memo (main process):** key = `sha256(sorted(name:size:mtimeMs))` over the censused file set, taken from Phase 1's stage A (`runPopulationSweep` returns the memo-key inputs, `phase-01:257`) — **`asOf` is NOT part of the key** (a run-varying component means zero memo hits, leaving the only warm mechanism permanently cold; no rollup, no cursor, no projection). Stage A is **metadata-only** (`readdir` + `stat` per entry, no file content read); every content hash, parse and admission stays in the worker. `asOf` travels in the envelope as the snapshot time of the pass that produced it, so a memo hit returns the original stamp rather than a fresh clock reading and the UI shows that stamp. No TTL; one entry, evicted on key change. Named limitation: a same-size in-place rewrite that also preserves `mtimeMs` is invisible to the key, so the memo can serve that one stale envelope — the CLI (`--no-memo`), `clearCache()`, and the fact that a real in-place rewrite advances `mtime` (Phase 1's X9/X10 rows) are the escapes, and the live-race checks live in Phase 6's acceptance receipt.
  - New IPC channel `antifan:mcp-dispatch:get-state`, read-only and **gated** with `isTrustedSessionVaultSender` (`src/main/browser/local-session-vault.ts:65-89`). When the sender fails the gate the handler returns a **well-formed `UNMEASURED` envelope** — never `null` (the renderer must never have to distinguish `null` from a payload). The gate's own behaviour is already pinned by `test/main/local-session-vault.test.ts:181-199`.
  - **The wire payload is a projection (plan.md constraint D). No raw frame crosses IPC.** Every persisted frame carries a required `authoritySnapshot` (`src/main/session/invocation-ledger.ts:32`) including `runtimeLeaseToken` (`src/shared/control-plane-contracts.ts:342`), `runtimePid`, `runId`, `attemptId` and `browserTarget.tabId`, plus `requestId`, `paramDigest` and `error.details`. The payload exposes **aggregate fields only**: top-level `status, reasonCode, affected, evidenceRefs, asOf, storePath, census, fileRollups, rows, totals, reconciliation`; per-row `name, calls, frames, superseded, states, errors, latency, excludedLatency, firstSeen, lastSeen, lowerBound`. `fileRollups` is Phase 1's per-file roll-up (`{ file, quarantineLike, tempLike, frames, admitted, namedInvalid }`) and **must pass through the projection unchanged** — it carries file **names**, never absolute paths, and Phase 6's gate lists the same key, so the two allowlists are one contract rather than two. Additionally:
    - `storePath` is a **display label** — the **final path segment only** (e.g. `invocations`), never a drive letter, never a POSIX-absolute path, never a user name, and **never a separator**: Phase 1's hard rule (`phase-01:203`) forbids `/`, `\` and drive letters in this string, and a two-segment label can only reach its second segment *through* a separator, so "two segments" and "no separator" cannot both hold. The single canonical implementation is the accounting module's exported `storeDisplayLabel` — every surface (service envelope, CLI, Hub) must call it rather than restate a literal, or one store can be labelled two ways on two surfaces. The absolute path is printed by the CLI and written into the on-disk receipt. Its type is **`string | null`**, not `string`: Phase 1 freezes it as the label when a store was resolved and `null` when nothing resolved (the `NO_DATA_ROOT_RESOLVED` case), so the renderer must branch on `storePath === null` and show the `reasonCode` copy instead of the label. Rendering `null` as the text "null", or substituting an invented placeholder path, is forbidden — the unresolved case is a first-class state with its own copy, not a missing value.
    - **The covered window is rendered from Phase 1's fields, never re-derived.** A truncated payload carries `limits.windowNewestMtimeMs` / `windowOldestMtimeMs` (the newest and oldest `mtimeMs` among the files actually read); the truncation notice shows them so "partial: N of M files" reads as *recent activity*, not as all history. Phase 1 owns those two fields as their single source, so this phase must not compute a window from `census.files` or from row timestamps.
    - `affected[]` is projected the same way: the module's own envelope legitimately names the injected directory there (`phase-01:89` puts `[dir]` in `affected` for a budget expiry), so the boundary that crosses IPC reduces any location-shaped entry to the display-label form and keeps the absolute form in the CLI stdout. `affected[]` is therefore subject to the same no-absolute-path assertion as the rest of the payload, not exempted from it.
    - **Object keys are part of the payload, so they are projected too.** The projection sanitises keys recursively, not values alone: a location-shaped key becomes the fixed bucket name `UNRECOGNIZED` (the same literal Phase 3's aggregates use, `phase-03:29`), and colliding counts are **summed rather than dropped**, because a histogram key is a vocabulary entry and labelling a bucket with a store label would be a false statement about what it counts. The first revision sanitised values only, so a persisted `error.code` that read as a path was published as an object key and the build gate returned OK on it. The location predicate has exactly **one** definition — `isLocationShaped`, exported from `src/shared/mcp-dispatch-contracts.ts` and imported by both the reader and this projection; the service's private copy is deleted, because two copies of a predicate already diverged once (`storeDisplayLabel`, and a stale `affected` token in the CLI that no enum member produces).
    - `evidenceRefs` may contain **only** synthetic identifiers matching `/^census:[0-9a-f]{8,}#L\d+$/` (`phase-01:162`); never a path, never a frame field.
    - The payload carries `totals.quarantineMargin.label` and, when present, `totals.truncation` — the two labelled disclosures the tab must print verbatim (see R3).
  - **Gate rationale, stated against the four "ungated read-only precedent" channels.** `antifan:workflow:get-state` (`src/main/browser/native-tab-host.ts:2057-2070`) returns the workflow registry plus `capabilities.listAll()` — a catalogue every MCP client already sees; `antifan:core-health:get-state` (`:2226-2241`) and `:2242` return health counters; `antifan:capsule:list` (`:2248`) returns a directory listing. **This** channel returns cross-session operational history — per-tool volumes, terminal-state mixes, error-code histograms, latency — which is the first artefact of its class in this codebase. The toolbar document is the exact origin `isTrustedSessionVaultSender` whitelists (`local-session-vault.ts:78-80`: any `file:` top frame whose path ends in `toolbar.html` or contains `/renderer/`), so an injected script in this document must not be able to read the operator's dispatch history. Gate it; do not treat the precedent list as an equivalence.
  - **Every string the tab renders is escaped or assigned as text (plan.md constraint E).** Row values are not all catalogue-controlled: `frame.name` and `frame.error.code` are persisted values, and the house row idiom is `item.innerHTML = \`…\`` (`toolbar.ts:621-630`, safe only because `:623-626` explicitly calls `escapeHtml`). Therefore every interpolated string in the new tab's HTML templates passes `escapeHtml` (`toolbar.ts:1122`), and every non-template assignment uses `textContent` (precedent: `setBody` at `:847-849`). The payload-derived strings that reach the DOM: `rows[*].name` (from `frame.name`), `rows[*].errors` keys (the `frame.error.code` histogram keys), `rows[*].states` keys, `reasonCode`, `affected[*]` and `storePath`. `reconciliation.lines` are built from counts by Phase 3's own `reconcile` (not by the renderer), but they are assigned via `textContent` as well, so the rule is uniform and needs no per-field trust judgement. Because the histogram key is the persisted `frame.error.code`, seeding the payload's `errors` key in the renderer test is the renderer-side equivalent of seeding the frame field; Phase 3's aggregate test owns the frame-level half. This is a hard requirement with its own test row, not a style note.
  - **The renderer refresh is failure-tolerant.** `refreshMcpDispatchState()` wraps its bridge call in `try/catch` and renders a well-formed `UNMEASURED` on failure, mirroring `refreshCoreHealthState()` (`toolbar.ts:517-531`). This is the real hazard: a host that loads the **real** preload (`test/e2e/toolbar-qa-hub-empirical-probe.cjs:145`) without registering the new handler makes `ipcRenderer.invoke` **reject**.
  - **The Hub's own open path refreshes the tab.** `openWorkflowHub()` (`toolbar.ts:488-515`) awaits `refreshCoreHealthState()` at `:505`, then `renderHubList()` at `:507`, then dispatches per tab at `:508-514`. The new refresh must be awaited there too, so closing and re-opening the Hub — or the first open with the tab already active — does not render `null`/stale rows while sibling tabs refetch.
  - New Hub tab `mcp-dispatch`, rendered from the ledger population — **not** from the capability catalogue — as **one** panel plus a labelled `core.*` hole row (filled by Phase 5's proxy store, or naming the mechanism and the launch paths that cannot carry the environment variable).
  - CLI `scripts/antifan-mcp-dispatch-account.cjs` with `--store`, `--as-of`, `--json`, `--no-memo`, `--freeze`. **Store resolution is `--store` or `ANTIFAN_DATA_ROOT` only** (`ANTIFAN_DATA_ROOT` → `<root>/control-plane-v2/invocations`, matching `getControlPlaneDir` `src/main/config/storage-locations.ts:101-103` and the ledger's `partitionsDir` `invocation-ledger.ts:116`); with neither, it reports `UNMEASURED` and **has no repo-relative fallback**. The deleted precedent (`scripts/lib/build-report.mjs:792-796`) pushes `<REPO>/.antifan-data/…`, `<REPO>/../.antifan-data/…` and `<REPO>/.antifan-canary/…` unconditionally; on this machine `E:\Work\apps\AntiFan\.antifan-data` does not exist while the live store is `E:\Work\.antifan-data`, so that fallback would silently read the real store while the operator believes `--store` won — and it contradicts constraint A (the reader never resolves or guesses a location).
  - **`--json` emits two documents, not one flat blob:** `{ "storeAbsolute": <string|null>, "payload": { <the envelope> } }`. The absolute path is the CLI's to print — constraint D keeps it out of the *renderer* payload — and the first revision smeared it into the same object as a CLI-only key, so the project's own gate declared the CLI's output invalid (rule 1: `storeAbsolute` is not in the aggregate allowlist) while a consumer could not tell which keys were the payload. Splitting them makes `payload` exactly the document the renderer receives, which is what lets the gate be run against **real** reader output instead of only hand-written fixtures (`phase-06`). This is a **breaking change** for anyone parsing the old flat shape, and the receipt must state it rather than let it be discovered.
  - The CLI **reserves the `--core-attempts` seam now**: `main()` dispatches sections through a section table with the ledger section as its only member, so Phase 5 (`phase-05-core-proxy-emitter.md`) adds the `core-attempts` reader over the proxy store as a new section rather than restructuring argument handling. The section's content is Phase 5's; this phase only fixes its name and its insertion seam.
- **Non-functional:**
  - `src/main/diagnostics/mcp-dispatch-accounting.ts` imports no `electron` (it must be `require`-able from the CLI and loadable by the worker). Verified in Phase 2, re-verified here. `node:worker_threads` is a `node:*` import and keeps that property.
  - CLI memo is **off by default** (the CLI's job is determinism and a cold read, not speed); the service memo is on.
  - Determinism is a **CLI-only** property (`plan.md` Success Criteria): two CLI runs on one frozen copy are byte-identical over every store-derived value — i.e. modulo `asOf` and `census.limits.elapsedMs` (the pass's own wall-clock self-measurement, which can never be deterministic and must be **named**, never silently normalized away). **The Hub makes no byte-identity promise** and no Hub acceptance criterion may demand one — a frozen copy is byte-immutable by construction, so it exercises none of the live-store races; the live mid-read append and compaction rows live in Phase 6's acceptance receipt.
  - The 8th nav tab is CSS-safe with **no new rule**: `.hub-nav-strip` already scrolls (`src/renderer/toolbar.css:2142`) and the seven-tab pressure note (`:2138-2141`) becomes an eight-tab note only if the implementer chooses to extend that comment.

## Architecture

```
McpDispatchService (main process: memo + singleton + worker spawn — does no reader work)
    │  memoKey = sha256(sorted(name:size:mtimeMs))   ← stage A metadata sweep; asOf NOT in key
    │  Phase 1 owns the sweep, PASS_BUDGET_MS, terminate() and the caller-side bounded await
    │
    ├──► new Worker(.compiled/src/main/diagnostics/mcp-dispatch-accounting.js, { workerData })
    │        └── accountStore({storeDir, asOf, memo:false}) → runCensusPass → ONE content pass
    │            → fold → reconcile → projected envelope
    │            exactly ONE post: the envelope (MEASURED | UNMEASURED)
    │            budget expiry ⇒ terminate() ⇒ UNMEASURED/READ_BUDGET_EXCEEDED, no rows
    │            ceiling ⇒ rows, each lowerBound:true + totals.truncation("partial: N of M files")
    │
    ├──► ipcMain.handle('antifan:mcp-dispatch:get-state')   native-tab-host.ts (after :2247)
    │        isTrustedSessionVaultSender(event) false ⇒ well-formed UNMEASURED (never null)
    │        payload = aggregate projection only; storePath = display label
    │
    └──► scripts/antifan-mcp-dispatch-account.cjs
             --store | ANTIFAN_DATA_ROOT only (no repo-relative fallback) ⇒ else UNMEASURED
             requires .compiled/src/main/diagnostics/mcp-dispatch-accounting.js, calls accountStore
             in-process (Phase 1 `mode: 'in-process'`, yields every 25 files) — no Electron, no worker
             to prove determinism; section table: [ledger]  ← Phase 5 appends `core-attempts`

preload: src/preload/toolbar-preload.ts (after :131) → contextBridge exposure at :207
renderer: getApi()?.getMcpDispatchState?.() → refreshMcpDispatchState() (try/catch → UNMEASURED)
          setHubTab('mcp-dispatch') → renderHubList() → renderMcpDispatchList(search)
          openWorkflowHub() → await refreshMcpDispatchState() beside refreshCoreHealthState()
          rows into #hubItemsList; detail reuses #hubCoreDetail + #coreDetailCode
```

Two surface decisions that were **measured**, not assumed:

1. **New tab, not an extension of the existing `mcp` tab.** The `mcp` tab renders list rows in a fixed 340 px pane (`toolbar.css:2224-2226`) and its rows come from the **capability catalogue** (`native-tab-host.ts:2060-2067`). Putting ledger metrics on a catalogue row would misrepresent the advertised population as a measurement, and there is no honest container for the reconciliation invariants or for the never-dispatched population. Cost of the correct option: ten mechanical edits to `toolbar.ts` plus one structural HTML insert, **no new HTML container and no new CSS** — the Hub has no per-tab content container at all; it has two panes (`#hubItemsList` `toolbar.html:510`, `#hubDetailPane` `:514`) and four mutually-exclusive detail divs.
2. **Fire-and-forget fetch.** `setHubTab` is synchronous (`toolbar.ts:941`) and is called from exactly seven click listeners (`:2813-2819`). Making it `async` would change its signature and every call site, and would need more than the renderer harness's `flush(rounds = 8)` microtask drain. The new click listener therefore mirrors the existing precedent `toolbar.ts:802` (`void selectCoreItem(id)`).
