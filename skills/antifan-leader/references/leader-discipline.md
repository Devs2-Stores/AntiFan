# Leader never-list and discipline

Read before dispatching work and again before reporting a result to the user. `LJ` = `node E:/Work/apps/AntiFan/scripts/leader/leader-job.mjs` (see SKILL.md "Job ledger").

## 1. Dispatch mechanics, concurrency, reports
- Concurrency is your call: count live OMP workers in `terminal.list {includeBuffer:false}`; heavy jobs (theme edit + AntiFan verify + watcher) 3–5 at once, light jobs (read/report) more. Queue the rest and start one whenever a worker finishes. Waiting on several workers: use `LJ wait` (SKILL.md "Job ledger"), or short `terminal.wait` calls per worker. If the machine lags or a worker reports a rate limit (429), stop starting new workers until the running ones finish.
- Cost reference (measured 29/10/2026, Opus): one read-only QA worker turn ≈ $1.18 / 2.27M tokens / ~3 min; the FIRST message of every fresh OMP session alone ≈ $0.40 (system prompt + skills written to cache). Do not spawn extra sessions for trivial steps.
- Every job gets a folder `E:/Work/scratch/leader/<yymmdd-hhmm>-<slug>/` holding `<key>.prompt.md` (what you sent) and `<key>.report.md` (what the worker writes). Read reports from files, not from terminal text.
- Report contract details: first line `STATUS: DONE | PENDING | NEEDS_INPUT | FAILED`, then ≤ 600 chars summary, files changed, evidence (numbers/screenshots), the leader-report/1 json block, and for NEEDS_INPUT the exact question with 2–3 options. Then the worker ends the turn.
- Accept a report only if it was written AFTER your dispatch `writtenAt` (check file mtime) and its first line is a valid `STATUS:`. A turn can end idle because OMP stopped, crashed or was Esc'd; a report from an earlier round must not pass as this round's result. Use a new file per round (`<key>.r2.report.md`).
- A worker whose turn ended without a report file: read its last transcript lines (`terminal.list` buffer / its OMP session JSONL under `~/.omp/agent/sessions/`), then send one follow-up asking it to write the report.
- Report to the user as a table: key, project, STATUS, one-line result, what you did NOT verify. Batch every NEEDS_INPUT question into one message (use your `ask` tool if a choice), then relay each answer to its worker.

## 3. Other cases
- **Same change on many projects**: do it once on a pilot worker, have the user (or you, from the report) accept it, then send the remaining workers "apply exactly this diff/description, then verify on your storefront"; never let N workers redesign the same change.
- **One big task in one repo**: split into disjoint file sets; each writer works in its own `git worktree` (never two writers in one folder). Before removing a worktree that has a `node_modules` junction, delete the junction first (`cmd /c rmdir <wt>\node_modules`), then `git worktree remove`. Merge is your step after reading reports.
- **Long jobs**: start the command in a worker shell, `terminal.wait` on its done pattern / exit, then run the next step and report.

## 4. Never
- Touch feedback rows whose `host` is not `Taiz` (comment, Stage, Deadline, Tags, Priority, delete) — they belong to Lâm, Quốc and others.
- Push to a live theme, publish a theme, push a whole theme (no `--only`), force-push, or delete data without the user's answer.
- Re-dispatch a push a worker reported as `REFUSED_THEME_*` (the edit-guard hook refused it in the worker terminal, or a worker's `terminal.write` was refused with `POLICY_DENIED` + `REFUSED_THEME_*`: live theme, whole-theme push, `--force`, foreign theme id, Shopify write, publish/delete, complex command shape). It is NEEDS_INPUT for the user.
- Type into a terminal whose OMP is running (TERMINAL_BUSY exists for that reason).
- Spawn a second worker for a row another terminal is already working on.
- Change Stage/Deadline/Tags of rows outside the batch the user named.
- Set a job state by hand or edit `job.json`; only the `leader-job.mjs` CLI writes it.

## 5. Kỷ luật của Leader (rút ra 30/10/2026 sau khi user phản ánh)
1. KHÔNG kết thúc lượt khi còn worker đang chạy. Worker là phiên OMP riêng, chạy tiếp sau khi lượt Leader kết thúc và không có gì tự theo dõi nó. Sau khi giao việc (`dispatch` + `terminal.write`), chạy `node E:/Work/apps/AntiFan/scripts/leader/leader-job.mjs wait --job <dir>` bằng tool bash với `async:true, timeout:0`, rồi gọi tool `wait`; kết quả tự về khi mọi worker idle sau thời điểm giao hoặc khi có NEEDS_INPUT. Một vòng lặp trong cell `eval` sẽ chết khi lượt kết thúc và `terminal.wait` bị giới hạn 28 giây mỗi lần, nên đừng dùng chúng làm cơ chế chờ chính. Việc không có ledger (không phải feedback): lặp `terminal.wait condition=run-idle` (truyền `writtenAt` của lần giao làm `afterEventAt` và `minRunSeq`) cho tới khi mọi worker idle và file report tồn tại. Chỉ báo kết quả thật sau khi đã kiểm (mục 2).
2. KHÔNG tin report của worker. Tự kiểm trước khi nói "xong": `verify-sheet` (diff snapshot trước/sau và export lại CSV thật của sheet: chỉ đổi đúng các ô định đổi; số dòng và cột tick không đổi); đọc lại issue trên dashboard (đúng một comment mới, Stage/Deadline/Tags không đổi); tự đo storefront bằng `anti.browser.evaluate` (không chỉ dùng số của worker). Nói rõ phần NÀO chưa kiểm.
3. Số dòng của issue trên dashboard (`rowNumber`, `viewDetail(N)`, `quickUpdate(N,...)`) DỊCH khi dòng khác bị xoá hoặc chuyển. 30/10/2026 Seahorse2 là #289 lúc 13:35 và #288 lúc 14:05; #289 khi đó thuộc host Quốc. Định danh bằng `id` ổn định (ví dụ `originalFeedback.find(x=>String(x.id)===ID)`), và đặt guard `host === 'Taiz'` + shop + sheet id trong MỌI prompt giao worker, không chỉ số dòng. Lấy `rowNumber` từ chính danh sách vừa tải rồi mới gọi `quickUpdate`; tải lại và kiểm Stage theo `id`. Worker dừng với NEEDS_INPUT vì guard sai là hành vi ĐÚNG: kiểm lại rồi giao lại, không ghi đè.
4. Số dòng GViz lệch 1 so với dòng sheet thật (dùng export CSV, dòng = index + 1). Khớp dòng theo chữ cột "Mô tả"/"Công việc", không theo số.
5. Leader KHÔNG tự đẩy theme (user chốt 30/10/2026: Leader chỉ điều phối, kiểm tra, theo dõi). Worker gặp REFUSED_THEME_PUSH_LIVE trên theme live hoặc lệnh `shopify theme push` bị chặn là CHỦ ĐÍCH: ghi NEEDS_INPUT kèm đúng câu lệnh, Leader chuyển nguyên văn cho user tự chạy. Trước khi user push lên theme live, nhắc user rằng file chưa diff với remote có thể ghi đè sửa đổi trên shop.
6. KHÔNG dùng `force:true` để gõ vào OMP đang chạy: nó chỉ xếp hàng, không đảm bảo tới kịp trước bước không đảo ngược của lượt đang chạy (30/10/2026 lệnh "giữ lại" chỉ kịp nhờ may: worker đã tự dừng ở PENDING). Cách giữ duy nhất đáng tin là đặt điều kiện ngay trong prompt đầu; giao followup sau khi worker idle chỉ áp dụng cho bước CHƯA bắt đầu. Kiểm trạng thái thật (sheet, dashboard) thay vì giả định.
7. Xong việc và đã kiểm: ĐÓNG các worker đã idle bằng `terminal.close` (kèm split dev của chúng). Không để lại terminal worker mở sau khi báo xong. Worker vẫn phải mở cho tới khi vòng Done (mục 9) chạy xong, vì chỉ nó đặt được Stage Done.
8. Giải thích cho user: huy hiệu `←` tím ở Terminal Manager là worker, vương miện là Leader; liên kết là `workerOf` do `terminal.create` ghi.
9. Leader CHỈ được: tạo/đóng terminal worker, ghi prompt/followup, `terminal.write`/`terminal.wait`/`terminal.list {includeBuffer:false}`, chạy lệnh `leader-job.mjs`, đọc và đo (export CSV sheet, đọc dashboard, đo storefront bằng `anti.browser.evaluate`). Leader KHÔNG tự: ghi ô sheet, comment hay `quickUpdate` trên dashboard, sửa file theme, chạy `hrv|shopify|sapo theme ...`, thêm giỏ hàng/đặt hàng thử. Mọi thay đổi do worker làm. Stage Done chỉ do MỘT WORKER đặt, trong vòng follow-up, và chỉ khi đủ cả hai: (a) Leader kiểm PASS (`verify-sheet` báo mọi dòng thuộc Dev đã xong, số còn lại = 0, không chỉ các dòng đã có note) và (b) user đồng ý. Lượt đầu của worker không bao giờ đặt Done.
