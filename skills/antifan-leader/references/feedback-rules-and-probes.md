# Feedback-run rules, probes and caps

Rules accumulated from real runs; loaded when a job hits login, Trello, live-theme, caps or round-limit questions. Hook behaviour named here is enforced by the hooks; the text is the reason.

## Rules from feedback runs
- Close each worker when ITS session is done (user: "Xong phiên nào đóng Terminal phiên đó luôn nhé"): right after a job's close round is verified, or its final PENDING/FAILED report is verified, run `close-worker.mjs` for that job's terminals, then `LJ close`. Never keep it open for the other jobs. A worker waiting for the user's Done stays open only while the `ask` for that issue is being answered in the same turn; if no answer comes in that turn, close it and open a fresh terminal for the close round (`dispatch --kind close --mode fresh`). `LJ close` waits up to `--settle-ms` (default 5000) for the run file of an ended worker, so it can follow `close-worker.mjs` in the same command.
- One current dev note per issue (user: "bạn note mới mà ko biết xóa comment cũ đi, làm QA đọc bị loạn"): the worker header makes a worker that posts a new note delete the earlier note of the SAME job that it supersedes (matched by the exact `dashboard.commentText` of an earlier round's report: a Pending question that now has its answer, an older "đã fix" of the same item) and report `dashboard.commentsRemoved` / `removedTexts`. Every dashboard comment shows author "User", so a customer's comment, a colleague's, or an old dev note with no such record is left alone and named in the report: ask the user about those. Your dashboard check is then: the comment count changed by `commentsAdded - commentsRemoved` and every other comment has the same text as before. A count that dropped with no `commentsRemoved` in the report is NOT a dashboard bug by default: the user may have deleted the comment (#311, 11/11/2026). Say what you measured and ask.
- A PENDING report that says "không tái hiện được" is accepted only when its summary says "Kịch bản khách: đã chạy" with numbers, or "CHƯA chạy vì ..." with a code reading of that condition. Compare the customer's own words with what the worker ran; a different, easier case is a gap: dispatch a discriminating round BEFORE asking the user whether to keep Pending (#311 round 1 tested a one-tag product while the customer described adding a tag).
- Live-theme safety is in the worker header: a backup outside the project before the first edit, a `Liquid error` check after every push with an immediate rollback, probes only inside `{% capture %}` printed in an HTML comment, no new files on the theme. A follow-up prompt you write by hand for a live theme must not relax it, and a report without the backup path and the per-push check is incomplete.
- `hrv theme info --json` failing: the header makes the worker run `node E:/Work/apps/AntiFan/scripts/leader/hrv-token-probe.mjs` (read-only, one JSON line, no token) before NEEDS_INPUT, so the report carries the measured cause. `ok:false` with "Token hết hạn và không refresh được" is branch (b) of the §8 login bullet.
- Login NEEDS_INPUT: `validate-report` prints `onlyUser: true, reasons: ["login/credential"]` for every login question. `E:/Work/AGENTS.md` §8 (Level 0; user 09/11 and 10/11/2026) still lets you approve exactly `hrv whoiam`, `hrv refresh-all` and `hrv login --no-open` under its five conditions; for those three lines that bullet wins over §4b (`leader-discipline.md` §4b). A password, an OTP, any other login and any other account stay the user's. List the approval and every login command in the final report.
- Build the round-1 prompt with `LJ fill-task --job DIR --task-file task.md --customer-file customer.txt`: it fences the customer text with `untrusted.mjs` and replaces `{{TASK}}`. Write both files with the write tool. Do not assemble prompts in an eval cell: a cell whose strings merely name the theme CLI is refused (`REFUSED_LEADER_THEME_CLI`).
- Check `ownerKey` in every `terminal.create` result before dispatch. A folder with no AntiFan project returns none (plus a `warning: NO_PROJECT_OWNER`), and that worker's antifan-browser MCP is not connected: close it with `close-worker.mjs` (the Sidebar project the placement minted stays: tell the user) and create the worker at `E:/Work/customizes`, naming the project folder in the prompt as the cwd for CLI commands. `terminal.create` also records the owner in the registry (`workers[id].ownerKey`: `project:<id>` or `unassigned`) and `LJ dispatch` refuses such a worker (exit 4) unless `--allow-no-owner` (a task that needs no browser tool); a worker with no recorded owner (made before this existed) prints `ownerCheck:"unknown"` and is not refused. Needs the app restarted after the update.
- A PENDING job closes with `LJ close --without-done` straight from state `verified` (no `approve --force`), once the user agreed to leave it Pending.
- Rules from the second run on 11/11/2026 (#313, #316, #321):
  - Close the moment a round is verified. `wait-any` now rescans, so a round dispatched while it runs (a close round, a follow-up) still wakes it; before that fix the close round of #313 sat finished for 3 minutes until the user asked.   - The user's answer to an `ask` may be free text ("Chạy kiểm thêm 2 vòng"): treat it as a follow-up round with exactly that work, then ask again. A check-only round says so in its prompt (no new feature, no dashboard comment, no sheet write, no Stage change).

  - Never spawn `process.execPath` from an eval cell: there it is the `omp` binary, so `execFileSync(process.execPath, [script, ...])` starts a CHILD OMP AGENT that takes each argv as a user message, inherits your terminal id (Leader authority) and acts on its own. After adjudicating, read the result back from Core (`node E:/Work/apps/AntiFan/scripts/antifan-core.cjs candidates '{"status":"PROMOTED"}'`, also `REJECTED` and `SUPERSEDED`) and report those counts, not the counts you intended.   - The §8 login pre-approval in a round-1 task keeps condition (2b) word for word (only when `hrv theme info --json` fails AND the token probe says the token expired), and its orgId and email come from a source you can name (the folder's `.haravan-cli_local.json`, an earlier report of the same shop), never from a guess.

## Trello, login and lookups
- Trello card: tell the worker to run `LJ probe --name trello-card` and pass the printed expression unchanged to `anti.browser.evaluate` (navigate first; it waits at most ~9 s for the card back, returns `partial:true` plus `ready:{back,loading,title,description}` if it gave up; a cold card took 8.6 s to mount). It returns `{title, listName, labels, due, descriptionMasked, checklist, comments, attachments, shape}` and masks bare passwords/tokens in the page (`[masked:<len>]`), so a password never reaches the session JSONL. Both workers read `body.innerText` instead and the card's Admin password is in two logs: treat that password as exposed. A worker that must TYPE the password adds `--copy-secret [N]` (Trello tab active): the probe puts the N-th secret of the description into the clipboard and returns only `{copy:{copied,len,index,total,secrets:[{index,kind,len}]}}`; paste with `anti.agent.sequence`, then overwrite the clipboard with an empty string. `shape` shows which selectors matched; comments/checklist/attachment selectors are best effort (not seen on a card with data), so a zero there on a card that has them means the DOM changed.
- Telegram OTP: `LJ probe --name telegram-otp [--after <epochMs of the login click>]` returns `{topicOpen, newest:{ageSec,len,fromHaravan}, count, newerThanSend?}`, never a digit, and answers at once (evaluate dies at 15 s, so poll with `anti.browser.wait {condition:"timeout"}`). Details in skill `haravan-login-via-otp`.
- Lookups, all read-only, one JSON line, under `E:/Work/apps/AntiFan/scripts/leader/`: `shop-folder-index.mjs <name|domain> [--scratch]` (shop to folders and bindings, 30 ms instead of a 94 s recursive grep), `shop-org-resolve.mjs <domain> [--admin-orgid ID|--admin-url URL]` (final domain, X-ShopId, live theme id and role), `hrv-whoiam-find.mjs <orgId|name>` (one org of the fixed-width `whoiam` table, orgName column only, nothing written to disk, instead of 57 orgs plus warnings).
- orgId of a login approval line comes from the `orgid=` of the accounts.haravan.com / Admin redirect, the folder's `.haravan-cli_local.json` or `hrv-whoiam-find.mjs`; never infer it from X-ShopId (for atoha the two were equal, not proven in general). When a card carries an Admin password, tell the worker to sign in with email + password first and use an OTP only if one is demanded after the password (the Leader sent the first Trello workers OTP-first, which was the Leader's mistake). The Atoha "OTP never arrives" conclusion was wrong: the Telegram tab was opened with `activate:false` and froze; the code arrived about 100 s after the request. Activate the tab and reload its view before concluding. Naming the account's mailbox in the prompt is a hint for the worker, not a stop condition.
- Trello tab hygiene (Biluxuryvn worker): `cursor.click` on an empty spot closes the open card modal and the DOM is gone; the `trello-card` probe clicks nothing, so run it instead of clicking around. Admin themes page: `/admin/themes` is 404, the page is `/admin/sale_channels/online_store/themes` with its content in an iframe (`web.haravan.app/themes`): use `anti.browser.evaluate_frame` with `frameUrl`, and click by coordinates; copying a heavy live theme takes minutes and a shop holds at most 8 themes.
- Two workers logging in to two different Haravan accounts in the same AntiFan profile fight over the accounts.haravan.com session: serialise the login step (dispatch the second login only after the first worker reported its login done), and run `hrv login --no-open` BEFORE the Admin login so one accounts session serves both (one OTP instead of two).
- `wait` / `wait-any` also wake on a worker's early `STATUS: NEEDS_INPUT` in line 1 of its report while the round is still running (event `needs-input`, `early:true`, job stays `dispatched`). It fires ONCE per rewrite of the report file (the file's mtime is stored on the round as `earlyNeedsMtime`), so a worker that writes NEEDS_INPUT and keeps working does not wake you again; answer it, and a later rewrite wakes you again. Before this only `needs-me` (via `reportStatus`) and `wait-workers --mine` showed it. Running `wait-workers --mine` plus `needs-me` before each wait stays the cheapest way to see a whole fleet. Processes started before this change (a running `wait-any`) keep the old code until relaunched.
- Worker prompts: the templates now carry the hook-driven rules (new project folder by its own bash line; one hrv command per line; no `>` redirect of hrv output; no CLI name inside an `echo` string or heredoc, write friction with the write tool) and the Trello/login lines above. Do not paste them again by hand.

## Round ceilings, side-effect caps, worker tool gotchas
- Round ceilings have no override: `LJ dispatch` refuses (exit 4) the 9th round of any kind but close (`MAX_TOTAL_ROUNDS` 8) and the 3rd review round (`MAX_REVIEW_ROUNDS` 2). `--allow-extra-round` only lifts the 4-live/3-dead soft cap below those ceilings. The BILUX job ran 13 rounds ($42, 7 h) because review rounds never counted and the extra-round flag had no limit. At the ceiling stop, tell the user what is unresolved, and start a new job only if they say the work continues. An advisory/review pass whose target reports did not change since the last one finds the same things: do not dispatch it.
- Side-effect caps: `LJ dispatch ... --cap spend=30000 --cap joins=8 --forbid caption-edit` (repeatable; caps are integers greater than 0, use `--forbid` for "none") stores `caps` on the round and appends a "GIỚI HẠN HÀNH ĐỘNG" block to the worker prompt; the worker's report must carry `"caps": {"used": {"spend": N, "joins": N}, "forbiddenDone": []}`, and `validate-report` fails when `used` exceeds a cap, a counter is missing, or `forbiddenDone` is not empty (a NEEDS_INPUT report may omit the echo or list only some counters; values it does give are still checked). The prompt also tells the worker to run `python -m ttbdash.runcaps init <jobdir>/<slug>.rN.caps.json ...` in `E:/Work/ttb-dash` and export `TTB_RUN_CAPS`; only an action whose script calls `runcaps.charge` is blocked by code (exit 5 = refused). The echo is self-reported and everything else rests on it plus your own check of the ledger. Caps belong to ONE round: a follow-up dispatched without `--cap`/`--forbid` has no limit and its prompt carries no caps block, so repeat them on every follow-up.
- Worker headers start with a "Tool gotchas" block (bash blocks `cat/head/tail/find/sed -i/echo >`: use `read`/`grep`/`glob`/`edit`/`write`; bash `cwd` instead of `cd x &&`; `read` the exact lines right before an `edit`; one CLI command per line; `$TEMP` not `/tmp`). A hand-written follow-up prompt should not contradict it.
- `node E:/Work/apps/AntiFan/scripts/leader/cf-tail-count.mjs --worker NAME --minutes 2 [--org ORGID]` (or `--file tail.jsonl`, `--stdin`) runs `wrangler tail --format json` and prints one JSON line: events by outcome, HTTP status, route, org (from `orgid` in the URL or logs), exceptions and error logs. Use it instead of a hand-written parser.
