# ULTRA SCOUT REPORT — Notify Everything (E:\Work\apps\Notify Everything)

## 1. Project & Directory

Haravan public app "Notify Everything": order webhooks → Telegram notifications. `.workspace-context.json`: `platform: haravan`, `branch: f1genz`, `verification: verified`. Layout: `server/` (NestJS 10 + Express + Prisma/PostgreSQL + ioredis; `src/`, `test/` 13 files, `prisma/` schema+migration, `scripts/` dev-seed + dual-gated dev-purge-telegram), `client/` (React 18 + Vite + AntD + React Query, single dashboard route), `docs/` (env-contract, security-checklist, lifecycle, deploy, onboarding, journals), `scripts/check-no-secrets.ts`. README claims V1 complete, 107/107 tests green (journal says 113 after chat-id rework).

## 2. Architecture & Role

Two processes share one AppModule:
- **API** (`main.ts`): `bodyParser:false` → manual `express.json` with `verify: captureRawBody` so HMAC runs over exact bytes; content-type guard only on webhook path; manual CORS allowlist with `Vary: Origin`, OPTIONS→403 for disallowed origins; bounded `trust proxy`; `Cache-Control: no-store` on /api.
- **Worker** (`jobs/worker.ts`): `NestFactory.createApplicationContext`, owner=`hostname-uuid8`, polls `DeliveryService.processBatch(owner,5)`, sleeps `WORKER_POLL_INTERVAL_MS` only when idle, graceful SIGTERM/SIGINT.

Pipeline: `POST /api/oauth/install/webhooks` → per-IP rate limit → `HmacVerifierService.verifyWebhookBody` (hex|base64 signature, `timingSafeEqual` on decoded bytes) → `ORDER_TOPICS` allowlist → identity resolution (Redis `domain:*`→orgid preferred, else payload `orgid|org_id|organization_id`, numeric tolerated) → `WebhookEvent` insert keyed by `idempotencyKey` (`provider:{topic}:org:{orgid}:{webhook-id}` or sha256 fallback) → install lookup → `OrderNormalizerService` → `SafeOrderDto` (PII-minimized) → `NotificationRendererService` HTML → ONE tx: `NotificationDelivery` (dedupeKey `eventId:shopId`) + `OutboxEvent` (dedupeKey `outbox:eventId`, carries `lifecycleGeneration`) + event=`processed`.

Worker claim = single SQL statement: CTEs quarantine stale-generation rows and dead-letter exhausted rows, then `FOR UPDATE SKIP LOCKED` selects candidates, sets `status='processing'`, `leaseOwner`, `leaseExpiresAt`, `attempts++`. `processOne` re-fences: terminal delivery → complete; install uninstalled → delivery `disabled` + quarantine; generation mismatch → `disabled` + quarantine; connection disabled → `disabled` + quarantine; decrypt-at-send; `TelegramError` classified permanent (401/403/chat-not-found/too-long/unknown) vs retryable (429 honoring `retry_after`, 5xx, timeout, network) → `sent`/`retry`/`dead_letter`.

Auth: OAuth `authorization_code` login+install with Redis state+nonce (GETDEL one-time), manual OIDC verify (JWKS cache, kid forced-refresh, iss/aud/exp/nbf/iat/nonce, 60s skew), AES-256-GCM token storage, HS256 JWT HttpOnly cookie (Lax same-site, None+Secure cross-site via `siteHost` incl. multi-part public suffixes), one-time `hrv_handoff_*` codes exchanged at `/api/auth/session/exchange` behind origin-policy check. Telegram connect: `getMe` → `getUpdates` → newest `message.chat` (private/group/supergroup) → encrypt+persist → then send confirmation (persist-before-send, deliberate per journal Red Team #4).

## 4. Critical Edge Cases / Traps / Workarounds

1. **Uninstall flow is dead code (highest severity).** `UninstallService.uninstall()` has zero callers in `src/` — grep confirms only module registration + tests. `WebhookService.handle` drops everything outside `ORDER_TOPICS` as `unsupported_topic`, yet `WEBHOOK_SUBSCRIBE_TOPICS` subscribes `app/uninstalled`+`shop/update`. Result: uninstalling never wipes tokens, never disables TelegramConnection, never tombstones domains, never clears Redis maps/handoffs; `lifecycleGeneration` never increments so the fencing machinery never engages; **an uninstalled shop keeps receiving Telegram order notifications**. `normalizeWebhookTopic()` (which would route `app_uninstall_webhook`→`app/uninstalled`) is likewise dead outside tests. `docs/lifecycle.md` + README describe the flow as working — doc-vs-code drift.
2. **Dead guard via incomplete Prisma select.** `webhook.service.ts:~110` selects `{shopId, lifecycleGeneration}` then checks `install.status === 'uninstalled'` — `status` never selected → `undefined === 'uninstalled'` → guard never fires. Compounds #1: even if uninstall ran, webhook layer still enqueues deliveries (claim-time fence in `delivery.service.ts`, which DOES select `status`, is the only real backstop). Root enabler: `private readonly db: any = prisma as any` in every service defeats Prisma's select-type checking — the codebase-wide `as any` cast makes this bug class invisible to tsc.
3. **Telegram HTML injection → permanent dead_letter.** `notification-renderer.service.ts` interpolates `orderCode`, `status`, `financialStatus`, `fulfillmentStatus`, `shopName`, `createdAt` raw into a `parse_mode:'HTML'` message. A shop named `A & B` or containing `<` produces `400 can't parse entities` → `TELEGRAM_UNKNOWN` → `isPermanent` → delivery `dead_letter` → **all notifications for that shop silently die**. Missing `&<>` escaping before interpolation.
4. **Fail-open Redis fallback + false-positive readiness.** `RedisService` silently switches to a process-local Map when Redis isn't `ready|connect`. In production this degrades OAuth state (login on instance A, callback on B → fail), session handoffs, lifecycle locks (no mutual exclusion), and domain→orgid maps — with no signal. Worse, `ping()` returns `this.storage.size >= 0` (always true) when Redis is down → `/readyz` reports `redis: ok` while every Redis-backed control is broken. Fail-open where the env contract is otherwise fail-closed.
5. **Domain→orgid resolution has no DB fallback and prefers cache over signed payload.** `ShopDomainService.resolveOrgid` reads only Redis `domain:*`; the `ShopDomain` Postgres table (with tombstones) is never consulted. Redis flush → falls back to payload orgid; if payload lacks org fields → `400 Missing webhook orgid` → Haravan retries forever. And `resolveIdentity` prefers the cached mapping over the HMAC-signed payload `orgid` — a stale mapping misattributes events to the wrong tenant (narrow window: install overwrites the key, but uninstall — which would clear it — never runs, see #1).
6. **Non-canonical idempotency hash.** `payloadHash = sha256(JSON.stringify(payload))` is key-order-sensitive; when `x-haravan-webhook-id` is absent, a redelivery with reordered keys produces a new `idempotencyKey` → new WebhookEvent → new NotificationDelivery (dedupeKey is `eventId:shopId`, eventId differs) → **duplicate Telegram message**. Needs canonical stringify (sorted keys).
7. **No timeouts on Haravan API calls.** `haravan-api.service.ts` `exchangeCode`/`refreshToken`/`getShop`/`subscribeWebhooks` use bare `fetch` — unlike the Telegram client (AbortController + `TELEGRAM_SEND_TIMEOUT_MS`). A hung Haravan endpoint hangs the OAuth callback or install indefinitely.
8. **In-memory rate limiter + shared-IP fingerprinting.** `IngressRateLimitService` is a per-process Map → effective limit = configured × instance count, resets on deploy. Webhook POST fingerprinted by `req.ip` — all Haravan shops share Haravan egress IPs, so `WEBHOOK_RATE_LIMIT_MAX=300/60s` is a per-IP budget across ALL tenants; a busy platform can throttle legitimate shops. Rate-limit post-HMAC by orgid.
9. **Worker heartbeat false-negative.** `/readyz` infers worker liveness from `MAX(updatedAt)` of completed outbox rows in last 5min — an idle-but-healthy worker reports `'no activity in 5min'` → 503. Liveness must be probed directly (heartbeat key written by poll loop), not inferred from side-effect traffic.
10. **Claim-time `attempts++` semantics.** Outbox `attempts` counts claims, not sends — a crash-looping worker burns all 8 attempts in ~8×lease without a single Telegram call → premature `dead_letter`. `NotificationDelivery.attempts` separately tracks real sends; the two counters have different semantics and the outbox one is what dead-letters the job.
11. **Dead constant + dead import.** `MAX_SEND_ATTEMPTS = 3` in `delivery.service.ts` unused (real cap `delivery.maxAttempts ?? 8`); `normalizeShopDomain` imported unused in `webhook.service.ts`.
12. **Doc drift.** `deploy.md` references `HRV_WEBHOOK_SECRET` (doesn't exist — POST HMAC uses `HRV_CLIENT_SECRET`) and documents `GET /readyz?token=` while code requires `Authorization: Bearer`. `lifecycle.md` documents the uninstall webhook flow that never executes. `deploy.md` says "serve client dist/ from the API" but `main.ts` configures no static serving — CDN/reverse-proxy mandatory.
13. **Session JWT alg not pinned.** `verifySessionToken` verifies HMAC over `header.payload` but never asserts `header.alg === 'HS256'` — signature still required so not exploitable, but contract isn't pinned.
14. **getUpdates chat-discovery traps (documented in journal).** Latest-`update_id` selection can bind the wrong chat for shared/multi-group bots; Telegram purges updates after ~24h → re-`/start` required; 409 = bot has active webhook elsewhere; persist-before-send ordering prevents state-loss on send failure.
15. **Bot token in URL path** — inherited Telegram constraint (`/bot<token>/method`); every proxy/ALB access log can capture it; mitigation is infra log redaction (`/bot\d+:/`), recorded in security-checklist.
16. **Minor:** `delivery.controller.ts` throws bare `Error` (500) when `shopId` missing instead of 401; `conn.chatId!` non-null assertion can send `chat_id:null` → permanent dead_letter; `DATA_ENCRYPTION_KEY` length validated at `TokenEncryptionService` construction, not in `loadEnv` → prod can pass env validation then crash at DI; `verifyHmac` launch endpoint issues handoffs for uninstalled orgs (downstream APIs fail closed — low impact); `WebhookEvent.payload` column exists but raw payload deliberately not persisted (PII minimization) → no replay capability for failed events; `formatMoney` `vi-VN` locale depends on full-ICU Node.

## 5. Improvements for Super Core

**Platform semantics (record as `platform: haravan` facts):**
- Webhook HMAC header arrives as `x-haravan-hmacsha256` (variants: `x-haravan-hmac-sha256`, `x-haravan-hmac`); signature may be hex OR base64 — accept both, `timingSafeEqual` on decoded bytes. POST HMAC secret = app `HRV_CLIENT_SECRET`; GET challenge is Meta-style `hub.verify_token`/`hub.challenge` with a SEPARATE verify token.
- Topic aliases: `order/*` ↔ `orders/*`, `app_uninstall_webhook`/`app_uninstalled` → `app/uninstalled`, `shop_update` → `shop/update`. Normalize via mapping table before allowlist.
- Org identity fields: `orgid`/`org_id`/`organization_id`, may be numeric; domain hints in `shop_domain`/`domain` payload keys, `?shop`/`?shop_domain` query, `x-haravan-shop-domain` header.
- Install callback path convention `/grandservice`; `HRV_SCOPE_INSTALL` needs `grant_service`, webhook auto-subscribe needs `wh_api`; subscribe endpoint `https://webhook.haravan.com/api/subscribe`; shop API `https://apis.haravan.com/com/shop.json`.

**Anti-patterns to record:**
- *Lifecycle-topic subscription without a dispatcher* — subscribing `app/uninstalled` while the ingress allowlist drops it leaves the entire revocation path dead; always grep for a caller edge from webhook entry → lifecycle service before declaring the flow implemented.
- *Guard on unselected field* — `select` omitting the field a guard checks is silently dead; root cause is `prisma as any` casts defeating select-type checking. Rule: never cast Prisma client to `any` in services.
- *Fail-open cache fallback* — in-memory Map fallback for Redis in security-critical paths (OAuth state, locks, tenant maps) breaks multi-instance correctness silently; and a `ping()` that returns true while degraded makes readiness lie. Fail closed or emit a loud degraded signal.
- *Non-canonical idempotency hashing* — `JSON.stringify` key-order sensitivity creates duplicate-delivery windows; canonicalize before hashing.
- *HTML parse_mode interpolation without escaping* — provider markup modes turn unescaped tenant data into permanent delivery failures (400 can't-parse-entities → dead-letter), not just rendering bugs.
- *Readiness inferred from side-effects* — worker heartbeat from completed-job timestamps false-negatives on idle systems; probe the process directly.
- *Per-IP rate limits on provider webhooks* — provider egress IPs are shared across all tenants; fingerprint post-auth by tenant, not IP.
- *fetch without timeout on OAuth/token endpoints* — hangs the whole auth callback; every outbound call needs an AbortController budget.

**Fix patterns to record:** transactional outbox append in the same tx as the domain write; single-statement `FOR UPDATE SKIP LOCKED` claim with stale-quarantine + exhausted-dead-letter CTEs; lifecycle-generation fencing at BOTH claim-time and send-time (defense in depth — it caught the dead webhook-layer guard); PII-minimized SafeDto before persistence (raw webhook payload never stored); persist-before-send for connection verification; one-time GETDEL handoff codes instead of session tokens in redirect URLs; redact sensitive headers (`authorization|cookie|set-cookie|x-forwarded-*|cf-*`) before persisting webhook audit rows; `isSafeRedirect` triple-check (raw, decoded, URL-parsed + auth-prefix blocklist); env-schema cross-validation (scope↔feature flags, token≠secret, placeholder regex, TRUST_PROXY≠true).

**Workarounds:** Telegram bot token necessarily in URL path → infra-level `/bot\d+:/` log redaction; getUpdates 24h purge → onboarding instruction to re-`/start`; Telegram 409 → "bot used elsewhere" merchant-facing message.

## 6. Improvements for Haravan Theme Core Output

- **Settings contract validation should mirror `env.schema.ts`**: ThemeCompiler's `settings_schema.json` generator should adopt the same fail-closed contract style — a machine-readable contract doc (like `docs/env-contract.md`) generated from the schema, with cross-field checks (setting X required when feature flag Y enabled), placeholder/default detection, and a validator that refuses to emit a theme when required settings are missing. The env-contract's cross-validation rules (wh_api required when auto-subscribe) map directly to theme settings dependencies (e.g., `show_vendor` requires `vendor_source`).
- **Alias-normalization pattern for section/block types**: `normalizeWebhookTopic`'s mapping table is the same problem ThemeCompiler solves when normalizing section type aliases across Haravan/Sapo/Shopify — keep a single canonical map, and (lesson from this repo) WIRE it into the actual dispatch path, not just tests.
- **PII minimization as a renderer contract**: `SafeOrderDto` whitelists fields before rendering — the theme DOM sanitizer/`export_clean` pipeline should apply the same whitelist-not-pass-through rule to Liquid-exposed objects (customer/order/cart) and to captured DOM (strip `data-*` tokens, Livewire blobs, unhydrated modals) before snapshot/export.
- **Escape-before-interpolate rule**: the renderer's missing HTML escape is exactly the bug class a theme compiler must prevent when injecting merchant-controlled strings (shop name, product titles, settings text) into HTML/JS contexts — emit escaped-by-default interpolation in generated Liquid/HTML.
- **Localized label dictionaries**: `TOPIC_LABELS`/`STATUS_LABELS` (vi-VN) show the dictionary pattern for localized theme output — keep labels in typed maps keyed by canonical enum, never inline conditionals.

## 7. Improvements for AntiFan Core & Site Clone

**AntiFan Core:**
- *Verification-claim lifecycle should adopt the outbox lease model*: `anti.verification.*` claims map cleanly onto claim→lease→complete/quarantine with `leaseOwner`/`leaseExpiresAt` fencing — a claim under verification by one agent shouldn't be re-verified concurrently, and expired leases should auto-release. The `attempts`/`maxAttempts` → `dead_letter` progression gives claims bounded retry semantics.
- *Doc-vs-code drift detection*: this repo's docs claimed a working uninstall flow with zero callers — AntiFan verification should treat any documented flow as UNVERIFIED until a caller edge (entrypoint → service) is proven, and `verification.record_claim` should carry a "caller-edge exists" proof obligation.
- *Sanitize before capture*: `redactHeaders` before persisting webhook headers is the same obligation SnapDOM/`export_clean` has for captured pages — strip tokens in DOM attributes, `Set-Cookie`/auth headers, and Livewire/SSR blobs before artifacts are stored or diffed.
- *Liveness probes must not infer from side-effects*: the `/readyz` worker-heartbeat false-negative is a general telemetry lesson — CDP/browser liveness checks should probe the target directly (evaluate/ping), not infer health from completed-job timestamps.
- *`isSafeRedirect` as reference implementation* for any navigation/redirect validation in browser automation (raw + decoded + URL-parse + prefix blocklist).

**Site Clone (@antifan/site-clone):**
- *Canonical hashing for IR dedupe*: the `JSON.stringify` key-order trap applies directly to IR node hashing and asset dedupe — canonicalize (sorted keys, stable serialization) before hashing or re-runs produce duplicate components/assets.
- *schemaVersion + producerVersion on every envelope*: `OutboxEvent` carries both — clone IR nodes and offline-standalone manifests should carry the same pair so replay/migration can fence incompatible artifacts.
- *Generation fencing for artifacts*: lifecycle-generation quarantine maps to clone-run generations — artifacts produced by an older IR generation must be quarantined, never served, in offline standalone mode.
- *Contract-IR = SafeDto*: `SafeOrderDto` decouples the notification contract from the provider payload via a whitelist — Site Clone's component contract IR should whitelist props rather than pass through scraped DOM attributes verbatim (same escape-before-interpolate obligation when IR renders to HTML).
- *Idempotent re-run design*: dedupeKey + unique constraint + P2002→`{duplicate:true}` is the model for clone run idempotency — re-running a clone must converge, not duplicate.
- *DoD validator evidence model*: this repo's env-contract + security-checklist + journal trail (every risk has file:line, every fix has a regression guard) is the evidence density the DoD validator should require — including honest inherited-risk entries (bot-token-in-URL) rather than silent acceptance.
